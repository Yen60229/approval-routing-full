## App 3 — 表單路由設定表 `form_route_config`

**App ID**：**待建立後補**（填入 `core/01-config.js` 的 `APP_ID.FORM_ROUTE_CONFIG`）

> **維護者是 IT／表單窗口，不是 HR。** HR 管「人與角色」（685/686），
> 表單窗口管「這張單走什麼流程」。因此本表不需要對使用者隱藏代碼欄位。

### 主表

| # | 欄位代碼 | 顯示名稱 | 類型 | 必填 | 唯一鍵 | 預設值 | 說明 |
|:-:|---------|---------|------|:----:|:------:|--------|------|
| 1 | `form_app_id` | 表單 App ID | 數值 | ✓ | ✓ | | 申請 App 的 kintone App ID；adapter 以 `kintone.app.getId()` 查此欄 |
| 2 | `form_name` | 表單名稱 | 文字（單行） | ✓ | | | 例：「採購申請單」，給維護者看 |
| 3 | `is_active` | 啟用狀態 | 核取方塊 | | | 勾選 | 選項：「啟用中」。未啟用時 adapter 走 fallback 全鏈 |
| 4 | `route_steps` | 路由關卡 | 表格（子表格） | ✓ | | | 有序，見下 |
| 5 | `max_depth` | 最大關卡數 K | 數值 | | | | **產生器算完回寫，不要人工填** |
| 6 | `cancel_groups` | 可作廢群組 | 群組選擇（多選） | | | | 產生器用：每個非終態掛「作廢」動作限定這些群組 |
| 7 | `reject_target` | 駁回退回 | 單選按鈕 | ✓ | | 退回申請人 | 選項：`退回申請人` / `退回上一關` |
| 8 | `deployed_at` | 上次部署時間 | 日期時間 | | | | 產生器回寫 |
| 9 | `deployed_hash` | 部署版本指紋 | 文字（單行） | | | | 產生器回寫；比對得出「路由改了但沒重跑產生器」 |

### 子表格 `route_steps`

| 欄位代碼 | 顯示名稱 | 類型 | 適用段類型 | 說明 |
|---------|---------|------|-----------|------|
| `step_no` | 順序 | 數值 | 兩者 | 段的執行順序 |
| `segment_type` | 段類型 | 單選按鈕 | — | 選項：`員工鏈段` / `指定角色段` |
| `stop_at_title_level` | 簽到職稱為止 | 下拉式選單 | 員工鏈段 | **選項須與 685 `title_level` 完全相同**（程式載入時比對，不一致會警告） |
| `skip_title_levels` | 跳過的職稱 | 複選（`MULTI_SELECT`；`CHECK_BOX` 亦可，值都是字串陣列） | 員工鏈段 | 同上選項；沿鏈經過但**不列入簽核**的職稱層級 |
| `role_id` | 指定角色 | 文字（單行） | 指定角色段 | 由程式提供可搜尋下拉，畫面顯示 role_name |
| `step_signing_mode` | 簽核模式 | 單選按鈕 | 兩者 | 選項：`（沿用角色表）` / `任一人簽` / `全員會簽`。兩種段類型都可指定全員會簽（該關會停在專屬的「會簽中」狀態，與位置無關） |

**`stop_at_title_level` 與 `skip_title_levels` 的差別**：前者決定走到哪裡**停**，後者決定路上哪幾層**不簽**。兩者可並用，例如「走到部長為止，但中間不簽次長」。

**段可任意排列**：`員工鏈段 → 指定角色段 → 員工鏈段` 是合法的——這就是「穿插經辦人」。

### 版面建議

[reject_target (寬度 30%)]        [cancel_groups (寬度 50%)]
[route_steps 子表格 (寬度 100%)]
[max_depth (20%)] [deployed_at (30%)] [deployed_hash (30%)]  ← 三個都是程式回寫，可設唯讀

## 申請 App 規約欄位（P8 標準 adapter 用，每個申請 App 都要埋）

| 欄位代碼 | 類型 | 說明 |
|---------|------|------|
| `approver_chain` | 表格（子表格） | 上表 |
| `current_approvers` | 使用者選擇（多選） | 目前這一關期望執行者的**鏡像**（介面顯示 + 原生流程「指定欄位」的 fallback）。流程狀態的實際執行者由 adapter 呼叫「更新執行者 API」（`PUT /k/v1/record/assignees`）設定——proceed 直接寫欄位在「指定欄位」下常失效，見 docs/06 §5.3、對話脈絡 §9.8 |
| `current_step` | 數值 | 目前第幾關。**0＝尚未進入簽核**（草稿／駁回）。狀態名不再帶關卡序，這一欄是關卡的唯一真相 |
| `total_steps` | 數值 | 鏈總長，顯示「第 3 / 5 關」用 |
| `next_state` | 文字（單行） | **按下「同意」之後要去哪個狀態**。值必為狀態模板之一 |
| `reject_state` | 文字（單行） | **按下「駁回」之後要去哪個狀態** |

> 原生流程管理每個簽核狀態的執行者仍設「指定欄位 → `current_approvers`」（更新執行者 API 只在狀態已設定執行者時可呼叫）。
>
> **為什麼需要 `next_state` / `reject_state`**：狀態固定 7 個、不帶關卡序號，靠自迴圈跑完
> 任意長度的鏈（見下節）。所以光看「簽核中」無從得知下一站是主管、經辦、會簽還是已簽完——
> 由 adapter 先算好寫進欄位，kintone 的動作 `filterCond` 讀它決定往哪走。
> 這兩欄必須在**按鈕按下前**就是正確的（kintone 解析 filterCond 與「指定欄位」執行者，
> 用的都是按下前的欄位值），所以 adapter 是在「進入某一關時」就寫好下一步的去向。

## 流程管理狀態模板（全公司統一，每個申請 App 逐字元相同）

7 個狀態、5 種動作，**與表單無關、與關卡數無關**：

| # | 狀態 | 執行者 | 說明 |
|:-:|------|--------|------|
| 0 | `草稿` | 建立者 | 可編輯、按「送出」進簽核 |
| 1 | `簽核中` | 指定欄位 `current_approvers`（任一人） | 員工鏈段的關卡 |
| 2 | `經辦人確認中` | 指定欄位 `current_approvers`（任一人） | 指定角色段的關卡 |
| 3 | `會簽中` | 指定欄位 `current_approvers`（**全員**） | 簽核模式為全員會簽的關卡 |
| 4 | `駁回` | 建立者 | 可修改後按「再申請」回草稿 |
| 5 | `核決` | 無 | 終態 |
| 6 | `作廢` | 無 | 終態 |

動作：`送出`（申請人）、`同意` / `駁回`（簽核者只看到這兩顆）、`再申請`（申請人）、
`作廢`（限定群組，SECONDARY）。

**關卡數不影響狀態圖**：kintone 允許動作的「執行前」與「執行後」是同一個狀態，
所以 N 關的鏈就在 `簽核中` 上自迴圈 N 次，每次由 adapter 換執行者。
組織多一層主管，流程設定一行都不用改。

⚠️ **`會簽中` 為什麼要獨立**：kintone 的執行者類型（任一人 ANY／全員 ALL）是**每個狀態
靜態設定**的，不能依記錄切換。`簽核中` 與 `經辦人確認中` 被所有任一人簽的關卡共用、
型別只能是 ANY，所以需要全員會簽的關卡必須停在自己的狀態上。

### 申請 App 的記錄權限（P8）

標準 adapter 在 `process.proceed` 事件裡寫欄位，這要求**簽核者具備該筆記錄的編輯權限**（kintone 平台規則，繞不過）。安全的組合是：

1. **記錄權限用「狀態」當條件**：草稿時只有申請人可編輯；簽核中時簽核者群組可編輯
2. **JS 在 detail 頁把業務欄位設 `disabled`**
3. **變更履歷留稽核軌跡**（既有外掛負責）

⚠️ kintone 的**欄位權限無法依流程狀態切換**（記錄權限可以），所以技術上擋不住蓄意用 REST API 改單——但那已屬舞弊而非誤操作，且有履歷可查。

⚠️ **API token 絕不可寫進前端 JS**：自訂 JS 在使用者瀏覽器執行，token 等於對所有人公開。要用 token 更新記錄必須有 kintone 以外的執行環境。
