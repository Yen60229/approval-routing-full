# 設計筆記：每個決定為什麼這樣做

這份文件記錄專案從 2026-04 到現在，每個重要設計是怎麼來的、當時考慮過什麼、為什麼選這條路。
程式碼看得出「做了什麼」，這裡補的是「為什麼」。接手前請先讀完，可以少走很多冤枉路。

目前做到哪裡，請看 `Phase進度追蹤.md`，這份不記進度。

## 一、為什麼要重做

舊系統用「組織名稱 + 職稱」推算誰該簽：

```javascript
// 舊系統的寫法
case '課長':   // 依組織名稱查次長 → 查部長 → 寫死對應
case '次長':
case '部長':
// 另外還有 SPECIAL_DEPARTMENTS 等寫死的特例陣列
// 以及 processOrgName() 處理組織名稱字串
```

結果是：

- 組織改名，要改程式
- 職稱層級變動，要改 case
- 兩個部門中間插一個新部門，整套邏輯就崩了
- HR 完全沒辦法自己維護

## 二、設計怎麼一步步走到現在

### 第一版：每個人記住「我的下一關是誰」

像鏈結串列一樣，A 的下一關是 B，就在 A 身上記 B。要插入 P，只改 A→P、P→B。

問題是：課長一換人，底下 20 個人都指著舊課長，就得改 20 筆。

### 第二版：中間加一層「角色」

拆成兩張表：

- 員工 → 起點角色（員工起點對照表，App 686）
- 角色 → 下一個角色，以及這個角色現在是誰（角色定義表，App 685）

課長換人，只改角色表 1 筆，底下 20 個人自動跟著變。

### 第三版：讓 HR 看得懂、用得順

HR 不想看到 `role_id` 這種代碼，所以：

- 代碼由程式自動產生，HR 看不到
- 「下一關」改成下拉選單，用點的
- 加上簽核流程預覽，設定完馬上看得到結果

另外還有一個需求：**已經在跑的單，也要能換到新的簽核者**。做法是：

- 重要的關卡用「群組」當簽核者，IT 改群組成員，在途的單馬上生效
- 一般關卡直接指定個人
- 單子上記的是「角色代碼」而不是人，跑到那一關才去查現在是誰

最後一點是整個專案的核心，後面很多決定都是為了守住它。

## 三、一開始就談定的事

| 問題 | 決定 | 影響 |
|------|------|------|
| 專案定位 | 做成可重複使用的模組，各申請 App 都能接 | 對外統一用 `window.ApprovalRouting` |
| 上線方式 | 一次取代舊系統 | 要先試點，也要有出事時的退路 |
| 一關多人 | 重要關卡用群組，其他指定個人 | 加 `holder_type` 欄位讓 HR 自己選 |
| 稽核紀錄 | ISO 需要，但既有外掛已經在做 | 本系統不另做簽核紀錄表 |
| 裝置 | 電腦為主，手機能看就好 | 手機版只處理詳情頁顯示 |
| 規模 | 500+ 員工、80+ 角色 | 角色表整包快取，員工表用到才查 |
| 分工 | IT 管群組，HR 管角色表和起點表 | 權限要分清楚 |

**一句話總結架構**：兩張表（角色表 + 起點表）+ 一個共用子表格（`approver_chain`）+ 一個共用引擎。
組織異動（換人、插關、重組）全部改資料就好，程式碼不動。

## 四、舊系統踩過的雷

寫新程式時對照一下，不要再踩。

**1. 一直重複 `get()`**

```javascript
// 錯：每次都重新 get，資料可能不一致
kintone.app.record.get().record.xxx.value = 'a';
kintone.app.record.get().record.yyy.value = 'b';

// 對：get 一次，改完再 set
const rec = kintone.app.record.get();
rec.record.xxx.value = 'a';
rec.record.yyy.value = 'b';
kintone.app.record.set(rec);
```

**2. `setFieldShown` 寫在 `set()` 前面**：會失效，一定要放在 `set()` 之後。

**3. submit 事件沒加 `async` 就用 API**：API 還沒回來就 `return event` 了。handler 要寫成 `async`，用 `await`。

**4. 把不是使用者選擇的欄位當成使用者選擇欄位處理**：文字欄位去 `.map()` 會直接出錯，處理前先確認欄位型別。

## 六、後來陸續做的決定

### 6.1 角色名稱改成計算欄位（2026-05～06）

原本 `role_name` 是 HR 自己打字，常打錯、格式不一。改成：

- 拆成兩個下拉欄位：`unit_name`（單位）、`title_level`（職稱）
- `role_name` 改成計算欄位，由這兩欄自動組出來（目前畫面上的格式是「單位 - 職稱」）
- 單位的選項由 IT 維護，程式執行時去讀欄位設定，不寫死在程式裡

**要注意**：計算欄位不能用 API 寫值（官方文件明列）。新增角色時只寫 `unit_name` 和 `title_level`，
不要帶 `role_name`。tools/04、05、06 在 2026-10-28 已經全部改掉。

### 6.2 角色名稱才是「哪一關」，代碼只是內部用（2026-06-02）

Jimmy 的說法：

> 「role_id 在角色定義表不重要，簽核鏈去對應到正確角色就好。role_name 完全相同但 role_id 可能不同，比如同單位的『職員』。」

所以下拉選單：

- 同名的角色只出現一次（同名就是同一關）
- 顯示、選取、還原都看 `role_name`，只有寫入時才用 `role_id`
- 選項依單位分組排序，80 多個角色比較好找；不限制只能選同單位，因為簽核本來就可能跨單位往上

### 6.3 一筆角色記錄只掛一個人（2026-08-19）

Jimmy 的說法：

> 「任一人簽 的設計是避免之後有人休假，可以直接加入執行者給該人簽名。只要是 holder_user 就只能選一個人寫上去。」

規則：

- 一筆角色記錄 = 一個簽核者
- 同一關有 3 個人可以簽，就建 3 筆同名記錄，各掛一人
- 「任一人簽」是給 kintone 流程管理用的，有人休假時直接加執行者代簽，不用動角色表

檢查時：同名多筆是正常的；一筆掛兩個人以上、或同一個人在同一關佔兩筆，才是錯的。

這條規則確定之前，`tools/05` B 區會把人「加進所有同名記錄」，人數乘以筆數，重複掛了一大堆。
之後改成每人各建一筆新記錄，`tools/06` 也補上「一筆掛多人」的偵測和拆分。

### 6.4 起點和下一關要一起設（2026-08-20）

Jimmy 的需求：686 設了起點角色，685 那個角色就一定要有下一關。

原本這兩件事分在兩支工具：`tools/05` 只寫起點，`tools/07` 只寫下一關，中間就會漏出「有起點但走不下去」的人，送單時卡住。

「下一關已設定」的定義：`next_role_id` 有值，**或**勾了「是終點」。兩個都沒有才算斷掉。

補法分兩頭：

| 目的 | 做法 | 位置 |
|------|------|------|
| 不再產生新的斷點 | 選起點時，那一關若沒有下一關，同一列一起指定，沒補齊不能送出 | `tools/05` A 區 |
| 收拾已經壞掉的 | 找出「有起點但 685 缺角色或缺下一關」的關卡，批量補 | `tools/05` G 區 |

寫入順序是**先 685 再 686**：起點一建好那個人就能送單，如果下一關還沒補上會卡住；先補 685，就算第二步失敗也不會有人送不出單。

刻意不做的事：

- G 區不自動建角色。起點指到不存在的角色時只列出來。建角色要決定簽核者、單位、職稱，這是人的判斷。
- 不改已經設好的下一關，只補完全沒設的。

當天還踩到一個坑：A 區原本只看「686 有沒有這個人的記錄」，記錄在但起點角色是空的人，就被當成已經設好了。
改成看「有沒有填角色」，寫入也改成「有空白記錄就補，沒有才新建」，不會對同一人建兩筆。

**教訓**：「記錄存在」和「欄位有值」是兩回事，做涵蓋率檢查一定要看值。

### 6.5 A 區可以直接新建角色（2026-08-20）

這跟 6.4「G 區不自動建」不衝突。A 區的一列就是「某單位某職稱的所有人」，建角色需要的資訊都有：
單位從組織名稱來、職稱從 kintone 職務來、簽核者就是這群人自己。G 區只有一個查不到的代碼，什麼都推不出來。

做法：

- 一關有幾個人就建幾筆同名記錄，各掛一人
- 起點指到最先建的那一筆（跟既有角色的配對規則一樣）
- 這個單位 + 職稱若已經有角色，就擋下來，請 HR 直接從清單選

讀欄位設定要用 REST API，不能用 `kintone.app.getFormFields()`。這支工具在 685 和 686 都會開，從 686 開會讀到 686 的欄位。

### 6.6 表單路由的設計定案（2026-08-31）

685、686 的資料補齊之後，Jimmy 提了兩個需求：

1. 每張表單的狀態名稱都一樣，不要寫死
2. 可以自己編排流程，例如只簽到某一層、中間插一個經辦人

談定的四件事：

| 問題 | 決定 | 影響 |
|------|------|------|
| 誰來挑簽核者 | 開發人員在一個設定表（App 736）裡設定 | 送單時不讓申請人自己勾；路由表由 IT 或表單窗口維護，不是 HR |
| 經辦人怎麼決定 | 路由表直接指定某個角色 | 就是「指定角色段」，不用新增結構 |
| 路由表和流程管理的關係 | 一起設計 | 流程管理的設定也放進路由表，不另外在 repo 放規格檔 |
| 試點 App | 新建一張測試表單 | 可以反覆部署、反覆試 |

設計上的兩個重點：

- **員工鏈段多了「跳過哪些職稱」**。原本只有「簽到哪個職稱為止」，表達不了「簽到部長，但中間不用次長簽」。
  跳過的關卡照樣沿著下一關往下走，只是不列入簽核名單，所以不是斷鏈。
- **不在 repo 另放規格檔**。路由在 kintone 裡，規格檔在 repo 裡，兩邊一定會不同步，而且不同步時沒人會發現。

**最重要的決定：每一關都在跑到時才查是誰，不做混搭。**

Jimmy 一開始的想法是「沒有編輯權限的關卡，用 API token 去更新」。方向沒錯，但有兩個問題：

- API token 不能放在前端。自訂 JS 是在使用者的瀏覽器跑的，token 寫進去等於公開給所有人。
- 有的關卡即時查、有的不是，兩邊的成本都要付：兩套邏輯、多一個設定欄位，出事時還要先搞清楚這關是哪一種。

「跑到時才查」是這個專案存在的理由，不能為了省一次權限設定就放掉。

權限的實際狀況：簽核者需要記錄的編輯權。防護方式是「記錄權限依狀態開放 + JS 把欄位鎖住 + 變更履歷可查」。
kintone 的欄位權限沒辦法依流程狀態切換，所以擋不住有人故意用 API 改單，但那已經是舞弊，履歷查得到。

**執行者怎麼換：改用「更新執行者 API」**

原本的想法是在按下核准的事件（`process.proceed`）裡改 `current_approvers` 欄位，讓下一關的執行者跟著變。
Jimmy 依實務經驗說這樣「有時候會失敗」。查過之後確認是已知行為：執行者設成「指定欄位」時，
kintone 用的是**按下按鈕前**的欄位值。

所以改成：

- 用 `PUT /k/v1/record/assignees`（更新執行者 API）為準。用登入者身分呼叫，不需要 token。
- `current_approvers` 欄位照樣寫，多數情況會成功，主要給畫面顯示用。
- 打開詳情頁時再檢查一次：目前的執行者跟即時查到的不一樣，就呼叫 API 補正。

### 6.7 路由引擎的幾個實作細節（2026-08-31）

- 沿鏈往下走的共用函式 `walkSegment` 放在 `core/03`，不放 `core/06`。因為 03 比 06 先載入，放在 06 的話 03 用不到。

### 6.9 續接段的兩個 bug（2026-09-01）

做下一階段前先把 P8 的程式整個看過一遍，找到兩個只在「員工鏈段 → 指定角色段 → 員工鏈段」才會出現的 bug。
當時的 20 個測試沒有一個是這種路由，所以一直沒被發現。

**1. 續接段的第一關被吃掉**

「主管送單不用簽自己」這條規則，被誤用在續接段。續接段的第一關是真正的上級，卻因為剛好是截止職稱被丟掉，名單少一個人，也沒有任何錯誤訊息。
修法：多傳一個參數，只有第一個員工鏈段才套用這條規則。

```
第 1 段 簽到次長  → 職員、課長、次長
第 2 段 指定角色  → 會計經辦
第 3 段 簽到部長  → 修正前：空的　修正後：部長
```

**2. 前一段已經走到終點，卻報「偵測到循環」**

程式把「還沒開始」和「已經走完」都當成 null，結果回到起點重走，馬上撞到走過的關卡。
真正的問題是路由設定矛盾，這個錯誤訊息會讓人往完全錯的方向查。修法是把三種狀態分清楚。

順帶補了 `step_no` 的檢查：要嘛全部留空，要嘛全部填而且不重複。混著填會讓留空的列跑到最前面。

**教訓**：「還沒開始」和「已經結束」一定要分開表示，不然錯誤訊息會指錯地方。

### 6.10 流程設定產生器：查文件推翻了三件事（2026-09-01）

寫產生器前把 kintone 流程管理的格式逐項查過，有三件原本用猜的事是錯的，而且錯了都不會報錯：

| 原本以為 | 實際上 | 錯了會怎樣 |
|---------|--------|-----------|
| `ONE` 是任一人簽 | `ONE` 是「指定其中一人」，任一人簽是 `ANY` | 每一關都要前一關的人手動挑下一個 |
| 使用者欄位用 `CUSTOM_FIELD` | 要用 `FIELD_ENTITY` | 每一關都沒人能簽 |
| 關卡變少就刪掉多的狀態 | 有單子停在上面的狀態不能刪，刪掉的名字也不能再用 | 改一次組織就永久浪費一個狀態名 |

**教訓**：平台 API 的選項，名字看起來像什麼不算數，一定要查文件。

（第三點後來因為 6.12 的改版整個不需要了。）

### 6.11 標準 adapter：官方一句話改掉了推進邏輯（2026-09-01）

原本的設計是「按一次核准，就往下一關」。但官方文件寫著：需要多人都按的關卡，每個人按都會觸發事件，**即使狀態沒有變**。

如果照「按一次就往下一關」，三人會簽的關卡被簽三次就會跳三關，中間兩關沒人簽，也不會報錯。

改法：看事件裡的「下一個狀態」決定要不要往下走。狀態沒變就代表會簽還沒簽完，只記錄簽名，不往下走。

其他三個決定：

- **狀態名稱只存一份**（`core/01-config.js` 的 `STATUS_TEMPLATE`）。產生器靠它建狀態，adapter 靠它認狀態。各存一份的話，改了名字 adapter 就默默認不得了。
- **內建欄位用型別找，不用欄位代碼找**。「狀態」「執行者」的欄位代碼會隨語言設定改變。
- **詳情頁的補正，比對的是即時查到的人**，不是送單時存下來的名單。這樣「事件沒生效」和「HR 換人了」兩種情況都補得到。

補正後會重新整理頁面，讓正確的人看到按鈕。連續兩次補不成功就停下來，請使用者找 IT，不會一直重整。

**教訓**：事件被觸發，不代表狀態有改變。

### 6.12 狀態模型改版：不再編號（2026-09-01）

Jimmy 提出：

> 「讓所有 APP 都不要寫死狀態名稱，都統一。4 種狀態：簽核中、經辦人確認中、駁回、核決(最後一關)。2 個動作：同意、駁回。」

原本的設計是「簽核中(1)、簽核中(2)…簽核中(K)」。名字雖然統一了，關卡數卻是寫死的：每張表單 K 不同，組織多一層就要重新部署，使用者看到「簽核中(3)」也不知道是什麼意思。

這個改法成不成立，取決於 kintone 允不允許「簽核中 → 簽核中」這種自己連回自己的動作。官方文件沒寫清楚，社群說不行。
請 Jimmy 實際開 kintone 試，**結果是可以**。如果當初照社群的說法做，會做出一套完全不需要的複雜設計。

改版後：

- 固定 7 個狀態：草稿、簽核中、經辦人確認中、會簽中、駁回、核決、作廢
- 每張申請表單的流程設定一字不差，關卡多少都不影響
- 原本為了「算 K」寫的一堆東西全部刪掉（計算最大深度、統計起點、狀態只增不減、會簽位置判定）
- 多了「會簽中」這個狀態給全員會簽用，而且現在放在哪一關都可以，比原本更彈性

新的問題：「會簽中 → 會簽中」可能是「還沒簽完」，也可能是「這關簽完了，下一關剛好也是會簽」。
所以改成看「是不是所有人都簽了」來判斷。

狀態不編號之後，流程的分歧條件沒東西可以看，所以申請 App 多了兩個欄位 `next_state`、`reject_state`，
由 adapter 在進入某一關時先算好下一步要去哪裡。

實際部署到測試 App（737）時，又遇到三條文件沒寫的規則：

| 錯誤訊息 | 規則 | 對策 |
|---------|------|------|
| 初始狀態下，執行者的 type 只能指定為「ONE」 | 第一個狀態只能用 `ONE` | 草稿改成 `ONE` |
| 初始狀態下，執行者需為空、或指定為記錄的建立人欄位 | 初始狀態不接受 `CREATOR` | 草稿的執行者留空 |
| `executableUser` 必填 | 次要動作一定要指定誰能按 | 沒設定誰能作廢時，就不產生作廢動作 |

這些都寫進產生器的檢查（`validateStatusPayload`），下次部署前就會先擋下來。
kintone 流程管理的文件只描述格式，不描述限制，這些只能靠實際部署試出來。

**教訓**：「不寫死」要同時看名字和數量。名字統一了、數量還跟著資料變，維護起來跟寫死差不多。

### 6.13 人事異動對照（2026-09-01）

Jimmy 的需求：職稱或單位跟 kintone 後台對不上時，要能很快查到、改好。

對不上的原因不同，改法剛好相反：

| 情況 | 怎麼判斷 | 怎麼改 |
|------|---------|--------|
| 單位改名 | 同一個單位底下**所有人**都對到同一個新單位（至少 2 人） | 直接改 `unit_name` |
| 關卡改名 | 同一關**所有人**都對到同一組新的單位職稱（至少 2 人） | 直接改單位和職稱 |
| 人員異動 | 同一關只有部分人對不上 | 換人接手：舊記錄改掛接任者，異動的人另外建一筆 |
| 無法判斷 | 後台沒有組織或職務資料 | 只列出來，請 IT 或 HR 補 |

人員異動**不能直接改單位職稱**：關卡名稱會跟著變，但角色代碼不變，而引擎是照代碼走的，
上一關會默默接到另一個職級。換人接手的話代碼完全不動，流程不受影響。

後台資料的讀取抽成 `core/08-directory.js`，`tools/05` 和 `tools/11` 共用。

### 6.16 未設定名單：不再一個一個設定（2026-10-28）

Jimmy 反映「涵蓋率一個一個設定超麻煩」。查下來各分頁的狀況：

| 分頁 | 原本 | 問題 | 改成 |
|------|------|------|------|
| A 未設定起點 | 依單位＋職稱分組，一組一列 | 已經是批次 | 不動 |
| B 不具簽核身分 | 勾人 → 底部選**一個**角色 → 送出 | 人散在各單位，一個單位做一輪，十幾個人就十幾輪 | 一人一列，自動帶入他自己那一關，勾好按一次 |
| C 已停用仍有起點 | 勾人 → 停用 | 已經是批次，但確認視窗只講筆數 | 確認視窗列出是誰、誰疑似回任 |
| D 已停用仍是簽核者 | 勾人 → 停用角色 | 同上 | 確認視窗列出誰掛在哪個角色 |
| E 姓名格式異常 | 只能看、匯出 | — | 維持不自動化（見下） |
| F 角色沒有簽核者 | 勾角色 → 停用 | 同 C | 確認視窗列出角色和上游數 |
| G 起點角色設定不完整 | 一列一個關卡 | 已經是批次 | 不動 |

B 區的預設角色怎麼來：

1. 先比單位＋職稱，跟 A 區同一套（員工的起點就是他自己那一關，§6.5）
2. 兼任或配不到，再看他在 686 的起點角色
3. 都沒有就紅底讓 HR 挑；可以先篩單位，再用「批次指定」一次填滿空白列
4. 只配「指定個人」的角色，群組成員還是 IT 在後台管

不會自動勾選。B 區裡可能有本來就不需要簽核的人，要 HR 看過才勾。

寫入結果：B/C/D/F 的寫入改成「某一批失敗不擋後面的批次」，結束時講成功幾筆、失敗幾筆。
kintone 一批（最多 100 筆）是整批成功或整批失敗，失敗那批沒寫進去，重新掃描後還在清單上，再勾一次就好。
A、G 有先後順序（先 685 再 686），維持遇錯就停。

刻意不做的事：

- **E 區不批次改名**：姓名在 cybozu 共通管理，改名要系統管理員權限；缺的中文或英文名也推不出來。用匯出 CSV 交給 IT。
