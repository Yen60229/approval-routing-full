## 一、痛點起源

Jimmy 接手的舊系統用「**組織名稱 + 職稱**」推導簽核者：

```javascript
// 舊系統長這樣
case '課長':
  // 根據組織名稱查次長 → 查部長 → 硬編碼對應
case '次長':
case '部長':
// + SPECIAL_DEPARTMENTS、DIRECTOR_CHECK_DEPARTMENTS 等硬編碼陣列
// + processOrgName() 字串處理組織名稱
```

**問題**：
- 組織名稱變動 → 要改程式
- 職稱層級變動 → 要改 case
- 組織之間插入新部門（如 A→B 之間插 P）→ 整個邏輯崩潰
- HR 無法自行維護

## 二、設計演進的三階段

### 階段 1：Linked List（純鏈結串列）

**想法**：每個員工只回答一個問題「我送出的單，下一關該給誰？」

- A 的下一關是 B → A 填 B
- 插入 P 只要改 A.next=P、P.next=B

**被否定的原因**：Jimmy 問「課長換人，該組織 20 人都要改 20 筆耶」。
**確實**：「指向某個具體人」的資料散落在 N 處，換人就要改 N 次。違反 DRY 原則。

### 階段 2：加角色抽象層（Indirection）

**核心洞察**：
> "All problems in computer science can be solved by another level of indirection." — David Wheeler

把資料拆成兩張表：
- 員工 → 起點角色（員工起點對照表）
- 角色 → 下一個角色 + 該角色目前是誰（角色定義表）

**換人變成 O(1)**：改角色表 1 筆資料，20 個員工自動跟著變。

### 階段 3：HR 友善 UI + 混合架構

Jimmy 擔心「HR 看到 role_id 這種代碼頭會痛」。

**解法**：
- 代碼由程式自動產生，HR 完全看不到
- `next_role_id` 改成下拉選單，HR 用點的不用打字
- 空白欄位加「鏈視覺化卡片」，讓 HR 看到設定後的結果

Jimmy 又提出需求：「**正在跑的舊單也要能用到新人**」。

**解法（混合架構）**：
- 重要角色的 `current_holder` 用 **GROUP_SELECT**（IT 改群組成員 → 舊單立即生效）
- 次要角色用 **USER_SELECT**（單純、直接指定個人）
- 子表格存的是**角色 ID** 而非具體人 → 跑到該關時才即時解析

## 四、最終架構（一句話）

> **兩張 App（角色表 + 起點表）+ 一個共用子表格（approver_chain）+ 一個核心引擎（window.ApprovalRouting）**

- **IT** 維護 kintone 群組成員
- **HR** 維護角色定義表 + 員工起點對照表
- **申請人**送單時，引擎自動沿 Linked List 產生簽核鏈
- **簽核時**即時解析群組/個人，拿到真實簽核者
- **組織異動**（換人/插入/重組）全部在資料層解決，程式碼完全不動

## 六、舊系統的具體雷區（給 Claude Code 的避雷指南）

從 Jimmy 之前的對話紀錄摘出：

### 雷 1：重複 get record
```javascript
// ❌ 錯：每用一次就 get 一次,資料不一致風險
kintone.app.record.get().record.xxx.value = 'a';
kintone.app.record.get().record.yyy.value = 'b';

// ✅ 對：一次 get、最後 set
const rec = kintone.app.record.get();
rec.record.xxx.value = 'a';
rec.record.yyy.value = 'b';
kintone.app.record.set(rec);
```

### 雷 2：setFieldShown 在 set 之前呼叫
```javascript
// ❌ 錯：順序反了,setFieldShown 失效
kintone.app.record.setFieldShown('xxx', false);
kintone.app.record.set(rec);

// ✅ 對：set 之後再呼叫
kintone.app.record.set(rec);
kintone.app.record.setFieldShown('xxx', false);
```

### 雷 3：submit event 沒 async 就用 await
```javascript
// ❌ 錯：handler 沒 async,API 還沒回來就 return
kintone.events.on('app.record.create.submit', (event) => {
  kintone.api(...).then(resp => { event.record.xxx = ... });
  return event; // API 還沒回來!
});

// ✅ 對
kintone.events.on('app.record.create.submit', async (event) => {
  const resp = await kintone.api(...);
  event.record.xxx = ...;
  return event;
});
```

### 雷 4：USER_SELECT 以外的欄位當 USER_SELECT 處理
```javascript
// ❌ 錯:文字欄位去 .map() 會炸
fields.forEach(f => {
  record[f].value.map(u => ({ code: u.code }));
});

// ✅ 對:先檢查欄位類型
const USER_SELECT_FIELDS = ['approver_1', 'approver_2'];
USER_SELECT_FIELDS.forEach(f => { /* 才 map */ });
```

### 雷 5：switch 裡面寫 return event 就不用 break
```javascript
// ✅ 這樣是對的,return 直接結束函數
switch (title) {
  case '課長':
    // ...
    return event;  // 不需要 break
}
```

## 九、Claude Code 階段的後續設計決策（2026-05～06）

### 9.1 role_name 改為計算欄位（unit_name + title_level）

**起因**：原本 role_name 是 HR 自由輸入的文字，容易打錯、格式不一。

**決策**（2026-05-01 起）：
- 拆出兩個下拉欄位 `unit_name`（單位）+ `title_level`（職稱）
- `role_name` 改為計算欄位，公式 `unit_name & "_" & title_level`
- unit_name 選項由 IT 維護，程式用 `getFormFields()` 動態載入（不再硬編碼 `TITLE_LEVEL_OPTIONS`）
- 詳情頁隱藏 unit_name / title_level，只顯示 role_name 計算結果（07-role-name-selector.js）

### 9.2 角色下拉：以 role_name 為業務識別，role_id 僅內部用

**Jimmy 的關鍵澄清**（2026-06-02）：
> 「role_id 在角色定義表不重要，簽核鏈去對應到正確角色就好。role_name 完全相同但 role_id 可能不同，比如同單位的『職員』。」

**設計影響**（套用於兩表下拉：`03-next-role-dropdown.js`、`01-entry-form-init.js`）：
- **完整 role_name 去重**：同名角色視為「同一關」，下拉只出現一次
- **識別改以 role_name 為準**：初始顯示、選取高亮、blur 還原全用 role_name；role_id 僅在寫入 `next_role_id` / `entry_role_id` 時使用
- **效果**：同名角色不論記錄存的是哪個 role_id，開啟編輯頁都能正確顯示，不會空白

### 9.3 下拉依 role_name 開頭（unit_name 單位）分組

**起因**：80+ 角色平鋪在下拉裡難找。

**決策**（2026-06-02）：
- 下拉選項依 unit_name 分組，組與組之間加單位標題列
- query `order by unit_name asc, role_name asc`，掃描時遇單位切換即插入標題
- 不限制可選範圍（簽核可跨單位往上），只是歸類讓 HR 好定位

### 9.5 holder_user 一筆記錄只掛一個人（2026-08-19 澄清）

**Jimmy 的關鍵澄清**：
> 「任一人簽 的設計是避免之後有人休假，可以直接加入執行者給該人簽名。只要是 holder_user 就只能選一個人寫上去。」

**規則**：
- 一筆角色記錄 = 一個簽核者。`holder_user` 永遠只有一個人
- 同一關有 N 個簽核者 → **N 筆同名角色記錄**，各掛一人（與 9.2「同名 role_name 可有多筆」一致）
- `signing_mode = 任一人簽` 不是拿來把多人塞進同一筆的，它是給 kintone 流程管理用的：
  有人休假時直接加「執行者」代簽，不必動角色表

**推論出的檢查規則**：
- ✅ 正常：同一個 role_name 有多筆記錄
- ❌ 違規：一筆記錄的 `holder_user` 有 2 人以上
- ❌ 違規：同一個人在同一個 role_name 底下有 2 筆以上記錄（同一關被掛兩次）

**踩過的雷**：`tools/05` B 區原本把勾選的人「附加」進**所有**同名記錄，
N 人 × M 筆同名記錄 = 同一人被重複掛在同一關的多筆記錄上。
2026-08-19 改為每人各建一筆新記錄，既有記錄一概不動；
`tools/06` 同步補上「一筆掛多人」的偵測與拆分功能。

### 9.6 起點（686）與下一關（685）必須同步設定（2026-08-20）

**Jimmy 的需求**：
> 「686 的 entry_role_id 如果有設定，在 685 就必須也要設定該角色以及下一關。
> 目前可能會有其中一邊沒有設定到的情況，希望可以同步進行設定。」

**問題根源**：這兩件事本來由兩支工具各做一半——
`tools/05` A 區只寫 686 的 `entry_role_id`，不管那個角色在 685 有沒有下一關；
`tools/07` 只寫 685 的 `next_role_id`，不管有沒有人以它為起點。
中間漏掉的組合就是「有起點卻走不動」：送單時 `buildChain()` 走到那一關無處可去。

**「下一關已設定」的定義**：`next_role_id` 有值 **或** 勾了 `is_chain_end`。
終點是刻意的鏈結尾，不是漏設；兩者皆無才是斷點。

**兩個方向各補一手**：

| 方向 | 做法 | 位置 |
|------|------|------|
| 防新的 | 選起點角色時，那一關若沒下一關就在同一列一併指定，補齊前勾不動 | `tools/05` A 分頁 |
| 修舊的 | 掃出 686 已設起點、685 卻缺角色或缺下一關的關卡，批量補齊 | `tools/05` G 分頁 |

**寫入順序刻意是先 685 再 686**：起點記錄一建好，那個人馬上就能送單，這時下一關
若還沒補上他會卡在建鏈；反過來先補 685，就算第二步失敗，685 也只是被補齊了設定，
不會有人因此送不出單。

**判斷與補設都以「同名記錄」為單位**：同名角色是同一關（見 9.2、9.5），
只補其中一筆，起點指到哪一筆就會走出不同的鏈。

**刻意不做的事**：
- **不自動建 685 角色**。起點指到不存在的角色時只列出來提示——新建角色要決定簽核者、
  單位、職稱，是人的判斷；工具代勞只會生出一堆沒有簽核者的空關卡，那正是 F 區的來源。
- **不改既有的下一關**。只補「完全沒設」的記錄，已經設好的一概不動；
  要改既有設定仍走 `tools/07` 批次設定下一關。

**當天踩到的坑：「有記錄」不等於「有起點」**

上線後 Jimmy 回報「很多記錄還沒設起點角色，A 區卻一個都沒列出來」。原因是 A 區
一直用「這個人在 686 有沒有記錄」判斷——`fetchEntryRecords()` 只要記錄裡出現這個
帳號就算數，`entry_role_id` 是不是空的完全沒看。記錄在、角色空白的人因此被當成
已設定；新加的 G 區又寫了 `if (!e.roleId) continue`，同一批人兩邊都漏掉。

修法：
- A 區改看 `assignedCodes`（記錄裡真的填了角色的帳號），「沒有記錄」與「有記錄
  但沒填角色」都算沒有起點
- 寫入從純新建改成 **upsert**：有空白記錄就補填原記錄，沒有記錄才新建。
  686 是一人一筆起點，對已有記錄的人再建一筆，`getEntryRoleId()`（`limit 1`）
  取到哪一筆就變成看運氣
- G 區維持只處理「有填角色但鏈壞掉」的情況，兩區職責不重疊

**判斷這類問題的通則**：欄位「有值」與記錄「存在」是兩件事，涵蓋率檢查一律要看值。

### 9.7 A 區可就地新建 685 角色（2026-08-20）

**Jimmy 的需求**：
> 「有些 685 還沒有設定好最一開始的起點角色，希望也能一起新增設定。單位＋職稱才是
> 角色名稱，目前要建立好才能選到該角色名稱，但目前還有一些沒建立完成。」

**為什麼這次可以自動建，G 區卻不行**（與 9.6 的「刻意不做」不衝突）：
A 區的一列就是「單位 X ＋ 職稱 Y 的所有人」，建角色需要的三樣東西全都在手上——
`unit_name` 從組織名稱、`title_level` 從 kintone 職務推、**簽核者就是這組同仁自己**。
G 區的孤兒起點只有一個查無此人的 `role_id`，什麼都推不出來，所以只能列出來提示。

**確認過的前提**：
- `walkChainStructure()` 從 `entryRoleId` 就開始 `push`，**起點角色本身是簽核鏈第 1 關**，
  所以新建的角色一定要有簽核者，否則第一關就沒人能簽
- `getRole(roleId)` 是 `roleCache.get(roleId)`，取**單筆**——一筆記錄就是一位簽核者，
  同名多筆不會被合併

**做法**：
- 一關有幾個人就建幾筆同名記錄，各掛一人（§9.5）
- 起點（686）指到這一關**最先建立**的那一筆，與 `matchEntryRole` 取記錄編號最小者
  同一個規則——既有角色與新建角色的行為才會一致
- `holder_type` 指定個人、`signing_mode` 任一人簽、`is_active` 啟用中；下一關沿用
  A 區既有的「下一關」欄，新角色一定要指定（可選終點）
- 選到的單位＋職稱若在 685 已經有角色，整列擋下來請 HR 直接從清單選，不重複建

**`role_name` 是計算欄位，不要寫**：目前公式是 `單位 - 職稱`（畫面上是灰的）。
`tools/04-batch-role-creator.js` 至今仍在 POST `role_name: unitName + '_' + titleLevel`，
停在 2026-06-02 改成計算欄位之前的舊格式——**這很可能就是「有些角色沒建立完成」的原因**，
待確認後修。本工具改成從 `/k/v1/app/form/fields` 讀型別決定寫不寫，
真要寫時分隔符號也從既有記錄反推，不寫死在程式裡。

**欄位設定讀取用 REST 不用 `kintone.app.getFormFields()`**：後者拿的是「目前這個 App」
的欄位，而這支工具在 685 與 686 兩張表的列表頁都掛著，從 686 開會拿到 686 的欄位。

### 9.8 P8 表單路由與流程管理的設計定案（2026-08-31）

**起因**：685／686 建置完畢、資料靠 tools/05～09 補齊後，Jimmy 提出兩個需求——
(1) 每個表單的狀態名稱都相同、不用寫死；(2) 可自由編排流程，選擇部分簽核鏈上的人、
或穿插經辦人。

**確認過的四個決策**：

| 問題 | Jimmy 的選擇 | 設計影響 |
|------|------------|---------|
| 誰在什麼時候「選人」 | 開發人員在一個 App 設定 | 走設定期跳關，不做送單期勾選；路由表由 IT／表單窗口維護，非 HR |
| 經辦人由什麼決定 | 路由表指定固定角色 | 就是 docs/06 的「職能段」，零新增結構 |
| 路由表與流程管理的關係 | **要一起搭配著作設計** | 廢除 docs/06 原本的 repo spec 檔，流程管理欄位進路由表主表 |
| 試點 App | 全新建的測試表單 | 可反覆試 status.json 部署與回滾 |

**docs/06 因此升版 1.1，改了兩處**：

1. **員工鏈段補 `skip_title_levels`**。原設計只有 `stop_at_title_level`，那只能截斷鏈尾，
   表達不了「走到部長，但中間不簽次長」。截斷與跳關是兩件事，職責要分開。
   實作關鍵：命中跳過清單的角色**照樣沿 `next_role_id` 往下走，只是不 push 進結果**——
   跳關不是斷鏈。
2. **廢除 repo 的 spec 規格檔**。原設計把 K、會簽關卡、作廢群組放在 repo 的 spec 檔，
   但路由本身在 kintone——兩份設定必然不同步，而且不同步時沒有任何機制會發現。
   這正是本專案一路以來反對的模式（設定散落多處）。改成路由表是唯一設定源，
   同時驅動執行期建鏈與部署期產生狀態圖。

**最重要的一個決策：全部關卡一律即時解析，不做混合方案**

Jimmy 原本傾向「路由表針對每一關設定簽核者有沒有編輯權限，沒有的用 API token 更新」。
方向對，但有兩個問題：

- **API token 不能放前端**。kintone 自訂 JS 在使用者瀏覽器執行，token 寫進去等於
  對所有有 App 存取權的人公開。要用 token 就必須有 kintone 以外的執行環境，目前沒有。
- **依關卡取捨解析時機是最差解**。它同時付兩邊成本：兩套 proceed 邏輯、路由表多一個欄位、
  文件要解釋為什麼 A 關即時 B 關不即時、出事時第一個問題永遠是「這關是哪種」。
  而收益趨近於零——那些關卡的簽核者本來就要能按核准鈕，本來就在 App 裡有存取權。

**判準**：即時解析是本專案存在的理由（見 §二階段 3、§四），整套架構——角色抽象層、
Linked List、子表格存 role_id 而非存人——全都是為了它。不能為了省一次權限設定而放棄。

**權限的誠實結論**：簽核者需要記錄編輯權，防護組合是「記錄權限依狀態開放 + JS 設 disabled
+ 變更履歷稽核」。kintone 的**欄位權限無法依流程狀態切換**（記錄權限可以，欄位權限不行），
所以擋不住蓄意用 REST API 改單——但那已是舞弊而非誤操作，有履歷可查。

**尚未驗證的基石假設**（P8 第一件要做的事）：
> 在 `app.record.detail.process.proceed` 裡寫入 `current_approvers` 並 `return event`，
> 狀態轉移後新狀態的 assignee 是否採用新值？

整個 adapter 設計建立在這個行為上。**若不成立，proceed 那半要整個重來**，
所以必須用一支十行 JS 在測試 App 上先實測，不能靠推測。
