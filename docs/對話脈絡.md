## 一、痛點起源

Jimmy 接手的舊系統用「**組織名稱 + 職稱**」推導簽核者：

```javascript
// 舊系統長這樣
case '課長':
  // 根據組織名稱查次長 → 查部長 → 硬編碼對應
case '次長':
case '部長':
// + SPECIAL_DEPARTMENTS、DIRECTOR_CHECK_DEPARTMENTS 等硬編碼陣列
// + processOrgName() 字串處理組織名稱
```

**問題**：
- 組織名稱變動 → 要改程式
- 職稱層級變動 → 要改 case
- 組織之間插入新部門（如 A→B 之間插 P）→ 整個邏輯崩潰
- HR 無法自行維護

## 二、設計演進的三階段

### 階段 1：Linked List（純鏈結串列）

**想法**：每個員工只回答一個問題「我送出的單，下一關該給誰？」

- A 的下一關是 B → A 填 B
- 插入 P 只要改 A.next=P、P.next=B

**被否定的原因**：Jimmy 問「課長換人，該組織 20 人都要改 20 筆耶」。
**確實**：「指向某個具體人」的資料散落在 N 處，換人就要改 N 次。違反 DRY 原則。

### 階段 2：加角色抽象層（Indirection）

**核心洞察**：
> "All problems in computer science can be solved by another level of indirection." — David Wheeler

把資料拆成兩張表：
- 員工 → 起點角色（員工起點對照表）
- 角色 → 下一個角色 + 該角色目前是誰（角色定義表）

**換人變成 O(1)**：改角色表 1 筆資料，20 個員工自動跟著變。

### 階段 3：HR 友善 UI + 混合架構

Jimmy 擔心「HR 看到 role_id 這種代碼頭會痛」。

**解法**：
- 代碼由程式自動產生，HR 完全看不到
- `next_role_id` 改成下拉選單，HR 用點的不用打字
- 空白欄位加「鏈視覺化卡片」，讓 HR 看到設定後的結果

Jimmy 又提出需求：「**正在跑的舊單也要能用到新人**」。

**解法（混合架構）**：
- 重要角色的 `current_holder` 用 **GROUP_SELECT**（IT 改群組成員 → 舊單立即生效）
- 次要角色用 **USER_SELECT**（單純、直接指定個人）
- 子表格存的是**角色 ID** 而非具體人 → 跑到該關時才即時解析

## 四、最終架構（一句話）

> **兩張 App（角色表 + 起點表）+ 一個共用子表格（approver_chain）+ 一個核心引擎（window.ApprovalRouting）**

- **IT** 維護 kintone 群組成員
- **HR** 維護角色定義表 + 員工起點對照表
- **申請人**送單時，引擎自動沿 Linked List 產生簽核鏈
- **簽核時**即時解析群組/個人，拿到真實簽核者
- **組織異動**（換人/插入/重組）全部在資料層解決，程式碼完全不動

## 六、舊系統的具體雷區（給 Claude Code 的避雷指南）

從 Jimmy 之前的對話紀錄摘出：

### 雷 1：重複 get record
```javascript
// ❌ 錯：每用一次就 get 一次,資料不一致風險
kintone.app.record.get().record.xxx.value = 'a';
kintone.app.record.get().record.yyy.value = 'b';

// ✅ 對：一次 get、最後 set
const rec = kintone.app.record.get();
rec.record.xxx.value = 'a';
rec.record.yyy.value = 'b';
kintone.app.record.set(rec);
```

### 雷 2：setFieldShown 在 set 之前呼叫
```javascript
// ❌ 錯：順序反了,setFieldShown 失效
kintone.app.record.setFieldShown('xxx', false);
kintone.app.record.set(rec);

// ✅ 對：set 之後再呼叫
kintone.app.record.set(rec);
kintone.app.record.setFieldShown('xxx', false);
```

### 雷 3：submit event 沒 async 就用 await
```javascript
// ❌ 錯：handler 沒 async,API 還沒回來就 return
kintone.events.on('app.record.create.submit', (event) => {
  kintone.api(...).then(resp => { event.record.xxx = ... });
  return event; // API 還沒回來!
});

// ✅ 對
kintone.events.on('app.record.create.submit', async (event) => {
  const resp = await kintone.api(...);
  event.record.xxx = ...;
  return event;
});
```

### 雷 4：USER_SELECT 以外的欄位當 USER_SELECT 處理
```javascript
// ❌ 錯:文字欄位去 .map() 會炸
fields.forEach(f => {
  record[f].value.map(u => ({ code: u.code }));
});

// ✅ 對:先檢查欄位類型
const USER_SELECT_FIELDS = ['approver_1', 'approver_2'];
USER_SELECT_FIELDS.forEach(f => { /* 才 map */ });
```

### 雷 5：switch 裡面寫 return event 就不用 break
```javascript
// ✅ 這樣是對的,return 直接結束函數
switch (title) {
  case '課長':
    // ...
    return event;  // 不需要 break
}
```

## 九、Claude Code 階段的後續設計決策（2026-05～06）

### 9.1 role_name 改為計算欄位（unit_name + title_level）

**起因**：原本 role_name 是 HR 自由輸入的文字，容易打錯、格式不一。

**決策**（2026-05-01 起）：
- 拆出兩個下拉欄位 `unit_name`（單位）+ `title_level`（職稱）
- `role_name` 改為計算欄位，公式 `unit_name & "_" & title_level`
- unit_name 選項由 IT 維護，程式用 `getFormFields()` 動態載入（不再硬編碼 `TITLE_LEVEL_OPTIONS`）
- 詳情頁隱藏 unit_name / title_level，只顯示 role_name 計算結果（07-role-name-selector.js）

### 9.2 角色下拉：以 role_name 為業務識別，role_id 僅內部用

**Jimmy 的關鍵澄清**（2026-06-02）：
> 「role_id 在角色定義表不重要，簽核鏈去對應到正確角色就好。role_name 完全相同但 role_id 可能不同，比如同單位的『職員』。」

**設計影響**（套用於兩表下拉：`03-next-role-dropdown.js`、`01-entry-form-init.js`）：
- **完整 role_name 去重**：同名角色視為「同一關」，下拉只出現一次
- **識別改以 role_name 為準**：初始顯示、選取高亮、blur 還原全用 role_name；role_id 僅在寫入 `next_role_id` / `entry_role_id` 時使用
- **效果**：同名角色不論記錄存的是哪個 role_id，開啟編輯頁都能正確顯示，不會空白

### 9.3 下拉依 role_name 開頭（unit_name 單位）分組

**起因**：80+ 角色平鋪在下拉裡難找。

**決策**（2026-06-02）：
- 下拉選項依 unit_name 分組，組與組之間加單位標題列
- query `order by unit_name asc, role_name asc`，掃描時遇單位切換即插入標題
- 不限制可選範圍（簽核可跨單位往上），只是歸類讓 HR 好定位

### 9.5 holder_user 一筆記錄只掛一個人（2026-08-19 澄清）

**Jimmy 的關鍵澄清**：
> 「任一人簽 的設計是避免之後有人休假，可以直接加入執行者給該人簽名。只要是 holder_user 就只能選一個人寫上去。」

**規則**：
- 一筆角色記錄 = 一個簽核者。`holder_user` 永遠只有一個人
- 同一關有 N 個簽核者 → **N 筆同名角色記錄**，各掛一人（與 9.2「同名 role_name 可有多筆」一致）
- `signing_mode = 任一人簽` 不是拿來把多人塞進同一筆的，它是給 kintone 流程管理用的：
  有人休假時直接加「執行者」代簽，不必動角色表

**推論出的檢查規則**：
- ✅ 正常：同一個 role_name 有多筆記錄
- ❌ 違規：一筆記錄的 `holder_user` 有 2 人以上
- ❌ 違規：同一個人在同一個 role_name 底下有 2 筆以上記錄（同一關被掛兩次）

**踩過的雷**：`tools/05` B 區原本把勾選的人「附加」進**所有**同名記錄，
N 人 × M 筆同名記錄 = 同一人被重複掛在同一關的多筆記錄上。
2026-08-19 改為每人各建一筆新記錄，既有記錄一概不動；
`tools/06` 同步補上「一筆掛多人」的偵測與拆分功能。

### 9.6 起點（686）與下一關（685）必須同步設定（2026-08-20）

**Jimmy 的需求**：
> 「686 的 entry_role_id 如果有設定，在 685 就必須也要設定該角色以及下一關。
> 目前可能會有其中一邊沒有設定到的情況，希望可以同步進行設定。」

**問題根源**：這兩件事本來由兩支工具各做一半——
`tools/05` A 區只寫 686 的 `entry_role_id`，不管那個角色在 685 有沒有下一關；
`tools/07` 只寫 685 的 `next_role_id`，不管有沒有人以它為起點。
中間漏掉的組合就是「有起點卻走不動」：送單時 `buildChain()` 走到那一關無處可去。

**「下一關已設定」的定義**：`next_role_id` 有值 **或** 勾了 `is_chain_end`。
終點是刻意的鏈結尾，不是漏設；兩者皆無才是斷點。

**兩個方向各補一手**：

| 方向 | 做法 | 位置 |
|------|------|------|
| 防新的 | 選起點角色時，那一關若沒下一關就在同一列一併指定，補齊前勾不動 | `tools/05` A 分頁 |
| 修舊的 | 掃出 686 已設起點、685 卻缺角色或缺下一關的關卡，批量補齊 | `tools/05` G 分頁 |

**寫入順序刻意是先 685 再 686**：起點記錄一建好，那個人馬上就能送單，這時下一關
若還沒補上他會卡在建鏈；反過來先補 685，就算第二步失敗，685 也只是被補齊了設定，
不會有人因此送不出單。

**判斷與補設都以「同名記錄」為單位**：同名角色是同一關（見 9.2、9.5），
只補其中一筆，起點指到哪一筆就會走出不同的鏈。

**刻意不做的事**：
- **不自動建 685 角色**。起點指到不存在的角色時只列出來提示——新建角色要決定簽核者、
  單位、職稱，是人的判斷；工具代勞只會生出一堆沒有簽核者的空關卡，那正是 F 區的來源。
- **不改既有的下一關**。只補「完全沒設」的記錄，已經設好的一概不動；
  要改既有設定仍走 `tools/07` 批次設定下一關。

**當天踩到的坑：「有記錄」不等於「有起點」**

上線後 Jimmy 回報「很多記錄還沒設起點角色，A 區卻一個都沒列出來」。原因是 A 區
一直用「這個人在 686 有沒有記錄」判斷——`fetchEntryRecords()` 只要記錄裡出現這個
帳號就算數，`entry_role_id` 是不是空的完全沒看。記錄在、角色空白的人因此被當成
已設定；新加的 G 區又寫了 `if (!e.roleId) continue`，同一批人兩邊都漏掉。

修法：
- A 區改看 `assignedCodes`（記錄裡真的填了角色的帳號），「沒有記錄」與「有記錄
  但沒填角色」都算沒有起點
- 寫入從純新建改成 **upsert**：有空白記錄就補填原記錄，沒有記錄才新建。
  686 是一人一筆起點，對已有記錄的人再建一筆，`getEntryRoleId()`（`limit 1`）
  取到哪一筆就變成看運氣
- G 區維持只處理「有填角色但鏈壞掉」的情況，兩區職責不重疊

**判斷這類問題的通則**：欄位「有值」與記錄「存在」是兩件事，涵蓋率檢查一律要看值。

### 9.7 A 區可就地新建 685 角色（2026-08-20）

**Jimmy 的需求**：
> 「有些 685 還沒有設定好最一開始的起點角色，希望也能一起新增設定。單位＋職稱才是
> 角色名稱，目前要建立好才能選到該角色名稱，但目前還有一些沒建立完成。」

**為什麼這次可以自動建，G 區卻不行**（與 9.6 的「刻意不做」不衝突）：
A 區的一列就是「單位 X ＋ 職稱 Y 的所有人」，建角色需要的三樣東西全都在手上——
`unit_name` 從組織名稱、`title_level` 從 kintone 職務推、**簽核者就是這組同仁自己**。
G 區的孤兒起點只有一個查無此人的 `role_id`，什麼都推不出來，所以只能列出來提示。

**確認過的前提**：
- `walkChainStructure()` 從 `entryRoleId` 就開始 `push`，**起點角色本身是簽核鏈第 1 關**，
  所以新建的角色一定要有簽核者，否則第一關就沒人能簽
- `getRole(roleId)` 是 `roleCache.get(roleId)`，取**單筆**——一筆記錄就是一位簽核者，
  同名多筆不會被合併

**做法**：
- 一關有幾個人就建幾筆同名記錄，各掛一人（§9.5）
- 起點（686）指到這一關**最先建立**的那一筆，與 `matchEntryRole` 取記錄編號最小者
  同一個規則——既有角色與新建角色的行為才會一致
- `holder_type` 指定個人、`signing_mode` 任一人簽、`is_active` 啟用中；下一關沿用
  A 區既有的「下一關」欄，新角色一定要指定（可選終點）
- 選到的單位＋職稱若在 685 已經有角色，整列擋下來請 HR 直接從清單選，不重複建

**`role_name` 是計算欄位，不要寫**：目前公式是 `單位 - 職稱`（畫面上是灰的）。
`tools/04-batch-role-creator.js` 至今仍在 POST `role_name: unitName + '_' + titleLevel`，
停在 2026-06-02 改成計算欄位之前的舊格式——**這很可能就是「有些角色沒建立完成」的原因**，
待確認後修。本工具改成從 `/k/v1/app/form/fields` 讀型別決定寫不寫，
真要寫時分隔符號也從既有記錄反推，不寫死在程式裡。

**欄位設定讀取用 REST 不用 `kintone.app.getFormFields()`**：後者拿的是「目前這個 App」
的欄位，而這支工具在 685 與 686 兩張表的列表頁都掛著，從 686 開會拿到 686 的欄位。

### 9.8 P8 表單路由與流程管理的設計定案（2026-08-31）

**起因**：685／686 建置完畢、資料靠 tools/05～09 補齊後，Jimmy 提出兩個需求——
(1) 每個表單的狀態名稱都相同、不用寫死；(2) 可自由編排流程，選擇部分簽核鏈上的人、
或穿插經辦人。

**確認過的四個決策**：

| 問題 | Jimmy 的選擇 | 設計影響 |
|------|------------|---------|
| 誰在什麼時候「選人」 | 開發人員在一個 App 設定 | 走設定期跳關，不做送單期勾選；路由表由 IT／表單窗口維護，非 HR |
| 經辦人由什麼決定 | 路由表指定固定角色 | 就是 docs/06 的「職能段」，零新增結構 |
| 路由表與流程管理的關係 | **要一起搭配著作設計** | 廢除 docs/06 原本的 repo spec 檔，流程管理欄位進路由表主表 |
| 試點 App | 全新建的測試表單 | 可反覆試 status.json 部署與回滾 |

**docs/06 因此升版 1.1，改了兩處**：

1. **員工鏈段補 `skip_title_levels`**。原設計只有 `stop_at_title_level`，那只能截斷鏈尾，
   表達不了「走到部長，但中間不簽次長」。截斷與跳關是兩件事，職責要分開。
   實作關鍵：命中跳過清單的角色**照樣沿 `next_role_id` 往下走，只是不 push 進結果**——
   跳關不是斷鏈。
2. **廢除 repo 的 spec 規格檔**。原設計把 K、會簽關卡、作廢群組放在 repo 的 spec 檔，
   但路由本身在 kintone——兩份設定必然不同步，而且不同步時沒有任何機制會發現。
   這正是本專案一路以來反對的模式（設定散落多處）。改成路由表是唯一設定源，
   同時驅動執行期建鏈與部署期產生狀態圖。

**最重要的一個決策：全部關卡一律即時解析，不做混合方案**

Jimmy 原本傾向「路由表針對每一關設定簽核者有沒有編輯權限，沒有的用 API token 更新」。
方向對，但有兩個問題：

- **API token 不能放前端**。kintone 自訂 JS 在使用者瀏覽器執行，token 寫進去等於
  對所有有 App 存取權的人公開。要用 token 就必須有 kintone 以外的執行環境，目前沒有。
- **依關卡取捨解析時機是最差解**。它同時付兩邊成本：兩套 proceed 邏輯、路由表多一個欄位、
  文件要解釋為什麼 A 關即時 B 關不即時、出事時第一個問題永遠是「這關是哪種」。
  而收益趨近於零——那些關卡的簽核者本來就要能按核准鈕，本來就在 App 裡有存取權。

**判準**：即時解析是本專案存在的理由（見 §二階段 3、§四），整套架構——角色抽象層、
Linked List、子表格存 role_id 而非存人——全都是為了它。不能為了省一次權限設定而放棄。

**權限的誠實結論**：簽核者需要記錄編輯權，防護組合是「記錄權限依狀態開放 + JS 設 disabled
+ 變更履歷稽核」。kintone 的**欄位權限無法依流程狀態切換**（記錄權限可以，欄位權限不行），
所以擋不住蓄意用 REST API 改單——但那已是舞弊而非誤操作，有履歷可查。

**基石假設——已否決（2026-08-31）**：
> 在 `app.record.detail.process.proceed` 裡寫入 `current_approvers` 並 `return event`，
> 狀態轉移後新狀態的執行者是否採用新值？

Jimmy 依實務經驗回報：**這樣直接寫入「有時候會失敗」，要靠外掛才穩**。查 cybozu.dev 與
社群後確認這是已知行為——當狀態的執行者設為「指定欄位」時，kintone 是用**按鈕按下前**
的欄位值去解析執行者，proceed 內改了 `event.record` 再 `return event` 常常來不及被採用
（社群原話「ボタンを押す前の時点の…フィールドのユーザーが作業者になってしまう」）。

**決策：改用「更新執行者 API」（`PUT /k/v1/record/assignees`）為權威機制**（見 docs/06 §5.3）。
- 這是一等公民端點，不是「改欄位賭它生效」的路徑；用 `kintone.api` 以**登入者身分**呼叫，
  不需要 API token，仍符合「全部走前端」的限制。
- `current_approvers` 欄位降為 **介面顯示鏡像 + best-effort**：proceed 照舊寫（多數情況會過），
  `app.record.detail.show` 當**安全網**——狀態為簽核中(n) 但目前執行者 ≠ 子表格第 n 關的
  `expected_signers` 時，即時解析後呼叫更新執行者 API（帶 `revision`）補正。
- 「跑到時才即時解析」的語義完全不變，即時解析仍是本專案存在的理由。
- 原生流程管理每個簽核狀態的執行者仍掛「指定欄位 → `current_approvers`」當 fallback
  （更新執行者 API 只在狀態已設定執行者時可呼叫）。

### 9.11 段接續的兩個 bug（2026-09-01 全盤分析後修正）

Phase C／D 動工前先對 P8 程式碼做了一輪全盤體檢，掃出**員工鏈段續接**的兩個真 bug。
兩者都只在「員工鏈段 → 指定角色段 → 員工鏈段」這種路由才會發生，而 20 個 route-engine
測試裡**一個續段案例都沒有**，所以一路綠燈到現在。

**① 續段的第一關會被無聲吃掉**（`core/03-chain-builder.js`）

`walkSegment` 有一條規則：段的第 1 關就命中 `stop_at_title_level` → 不 push。
它的語義是「**申請人自己**就是截止職稱，主管送單不用簽自己」（§9.9、docs/06 §4）。
但 `walkSegment` 分不出這一段是從**申請人起點**開始、還是從 `personalCursor`
（前一段的下一關）續接——續段的第 1 關是貨真價實的上級簽核者，命中截止職稱
就被丟掉，**鏈上少一個人而且沒有任何錯誤訊息**。

修法：新增 `isEntrySegment` 參數，只有第一個員工鏈段傳 `true`。

```
第 1 段 stop=次長  → 職員、課長、次長      （游標＝部長）
第 2 段 指定角色                          會計_經辦
第 3 段 stop=部長  → 修正前：空的！        修正後：部長
```

**② 續段接在終點之後 → 誤報「偵測到循環」**（`core/06-route-engine.js`）

`personalCursor ?? (await resolveEntry())` 這個寫法把兩種 null 併成一種。
前一段若走到 `is_chain_end`，`nextRoleId` 是 `null`，`??` 讓它**退回申請人起點重走**，
`visited` 立刻命中 → 回「偵測到循環：ROLE_P1 重複出現」。真正的問題是路由設定矛盾
（前段已到終點、後面還掛員工鏈段），維護者拿著這則訊息會往完全錯的方向查。

修法：`personalCursor` 三態分清楚——`undefined`＝還沒有員工鏈段（從起點開始）、
`string`＝續接、`null`＝前段已到終點（明確報設定錯誤）。

**通則**：`??` 併掉的兩種 nullish 值，語義上常常是不同的東西。狀態機用哨兵值時，
「還沒開始」與「已經結束」一定要分開，否則錯誤訊息會指向錯的地方。

**順帶補上 `step_no` 驗證**（`apps/form-route/01-route-form.js`）：段的順序決定接續關係，
排錯等於鏈錯，而原本完全沒驗。引擎依 `step_no` 排序且 `Number('') === 0`，所以：
全部留空是安全的（排序穩定＝畫面列順序）、**混填**會讓留空的列竄到最前面、**重複**
會讓先後不確定。規則定為「要嘛全空、要嘛全填且不重複」。

測試：route-engine +4（含兩個 bug 的紅燈案例，修正前確認會失敗）、route-form +5。
**158 項全過**。

### 9.12 Phase C 產生器：查證推翻的三件事（2026-09-01）

動工前把 status.json 的 schema 從 cybozu.dev／kintone.dev 逐項查過，
**三件原本靠推測的事被推翻，每一件都會產生「不報錯但行為不對」的設定**：

| 以為的 | 實際的 | 錯了會怎樣 |
|--------|--------|-----------|
| `assignee.type = ONE` 是「任一人簽」 | `ONE` 是「**指定**一人來做」，任一人簽是 **`ANY`** | 每一關都要前一關的人手動挑下一個簽核者 |
| 使用者選擇欄位用 `CUSTOM_FIELD`（官方範例的 "Boss" 誤導） | 是 **`FIELD_ENTITY`**，`CUSTOM_FIELD` 是另一回事 | 執行者解析不到，每一關都沒人能簽 |
| K 變小就刪掉多餘的簽核狀態 | kintone **只能刪沒有記錄停在上面的狀態**，而且**刪掉的名字不能再用** | 一次組織調整就永久燒掉一個狀態名 |

第三點衍生出 docs/06 新增的 §5.6「**產生器只增不減**」。K 會隨組織上下浮動
（多一層主管就多一關），若照著「算出來幾關就設幾關」做，每次縮編都在消耗
不可回收的狀態名，而且只要有一張在途單卡在那一關，部署直接失敗。
實際使用的關卡數改成 `max(這次算出的 K, 已部署的簽核狀態數)`——多出來的狀態
沒有動作指向它，留著等同不存在。

**同時確認原設計無誤的一點**：同一個 from 可以有兩條**同名**動作 + 互補 `filterCond`，
這是 kintone 做 OR 分歧的標準手法，§5.2 用它處理「鏈深度因人而異」的設計成立。
唯一禁忌是兩條的 `filterCond` 同時為空。這是唯一無法從文件百分之百確認、
需要在測試 App 上看一眼的點（確認畫面上只出現**一顆**「核准」按鈕）。

**「全員會簽只能放在固定位置」比 docs/06 原本寫的更嚴格**：一個指定角色段的絕對位置
可以事先算出來，條件是它前面**每一段都是指定角色段**。只要前面有任何員工鏈段，
「會計經辦」對課員是第 5 關、對部長是第 2 關，沒有哪一個「簽核中(n)」能被靜態設成 ALL。
產生器的 `resolveAllSigningPositions` 擋下這種設定並說明原因，不默默產出行為不符預期的圖。

**`expandRouteSegments` 從 `buildChainForForm` 抽出來的理由**：算 K 要對 686 的每一個
distinct 起點角色各展開一次（~80 次）。走完整的建鏈會 `Promise.all` 解析 holder
（群組還要打 API），80 次的成本完全白付；更關鍵的是**任何一關暫時沒有簽核者就會
`ok:false`**——但 K 是結構問題，跟「今天那一關有沒有人」無關，不該因此算不出來。

**判斷通則**：平台 API 的列舉值，名字看起來像什麼不算數。`ONE`／`ANY`、
`FIELD_ENTITY`／`CUSTOM_FIELD` 這種選錯了不會報錯、只會行為不對的值，
一律查文件確認語義，不靠字面推測。

### 9.13 Phase D 標準 adapter：一條官方註記改掉了推進邏輯（2026-09-01）

adapter 的核心只有一句話：**「這次 proceed 之後，記錄該長什麼樣？」**
原本 docs/06 §5.3 寫的是「`current_step + 1`」，直覺、看起來沒問題。

但 kintone 官方文件在 `process.proceed` 事件頁有一句：

> Some processes need several assignees to perform an action before moving onto the next
> status — **this event will take place even when the status does not change.**

**全員會簽的關卡，每個執行者按一次都會觸發 `proceed`，而狀態不變**，直到最後一人才轉移。
用 `current_step + 1` 的話，一個三人會簽的關卡會在三個人各簽一次之後跳三關——
中間兩關直接被略過，沒有任何人簽到，而且不會報錯。

**改法**：推進一律由 `event.nextStatus` 驅動，不由「動作被觸發了」驅動。
`event.status === event.nextStatus` 就是「會簽還沒簽完」，這時只記 `signed_by`、不推進。
整段邏輯抽成純函式 `planProceed`，八個分支（stay／advance／terminal／reset／blocked）全部有測試。

**通則**：事件「被觸發」不等於「狀態改變了」。任何依賴事件推進狀態機的程式，
都要先確認事件與狀態轉移是不是一對一——這裡剛好不是。

**其他三個實作決定：**

- **狀態名模板移進 `core/01-config.js`**（`STATUS_TEMPLATE`）。產生器**建**狀態、
  adapter 從狀態名**反推**第幾關，兩邊必須用同一份字串。各存一份的話，
  哪天改個狀態名，adapter 會靜默認不得狀態——單子照跑，執行者全錯，而且不報錯。
- **內建欄位用「型別」找，不用欄位代碼找**。狀態／執行者的欄位代碼隨 kintone 語言設定
  而異（狀態／ステータス／Status），寫死任何一個都會在別的語言環境靜默失效。
  改成掃 `type === 'STATUS'` / `'STATUS_ASSIGNEE'`。
- **安全網比對的是「即時解析的結果」，不是子表格快照**。docs/06 原本寫「比對
  `expected_signers`」，但快照是送單當下的樣子——HR 換人之後它本身就是舊的，
  拿舊的去比對只補得了「proceed 沒生效」，補不了「角色換人」。改成即時解析後，
  兩種情況走同一條路徑。這也才對得起「跑到那一關才解析」這個設計初衷。

安全網補正成功後會**重整頁面**：執行者是頁面載入時由伺服器算出來的，不重整的話
正確的人看不到按鈕。補正後下一次載入會比對一致、不再重整，天然收斂；
另外用 sessionStorage 記補正次數，連續兩次沒成功就停手並提示找 IT，不無限重整。

### 9.14 狀態模型改版：編號消失（2026-09-01）

Phase C／D 做完當天，Jimmy 提出：

> 「讓所有 APP 都不要寫死狀態名稱，都統一。4 種狀態：簽核中、經辦人確認中、駁回、
>   核決(最後一關)。2 個動作：同意、駁回。」

**他是對的，而且指出了我沒看見的東西**：`簽核中(1)…簽核中(K)` 其實**還是寫死了**，
只是寫死的是「數量」而不是「名字」——K 因表單而異、組織長高就要重新部署每一張表單、
`簽核中(3)` 對使用者也毫無意義。

**整件事押在一個 kintone 行為上**：動作的「執行前」與「執行後」可不可以是同一個狀態
（`簽核中 --同意--> 簽核中` 自迴圈）。可以的話，N 關的鏈就在同一個狀態上迴圈 N 次，
每次由 adapter 換執行者，K 整個消失。

我查了官方三頁文件（`set_process` / `design_process` / 設定變更注意事項）**都沒明講**；
社群討論則一致指向「不行，要繞 dummy 狀態」。我給那個推測八成把握——**不足以定案，
所以請 Jimmy 開 kintone 試一次。結果是可以。社群的說法是錯的。**

**這是本專案至今最划算的一次「先問再做」**：照推測動手會做出一個完全不必要的複雜設計，
而且錯得很隱蔽（會以為是平台限制，不會回頭質疑）。

**改版後刪掉的東西**（都是編號模型的產物）：

| 刪掉的 | 原本在解決什麼 |
|--------|---------------|
| `computeMaxDepth`（掃 686 的 distinct 起點各展開一次） | 算 K |
| `getDistinctEntryRoleIds` | 同上的資料來源 |
| `max_depth` 欄位的計算與 submit 檢查 | 擋「鏈比已部署狀態多」 |
| 「產生器只增不減」整套邏輯（§9.12 第 3 點） | K 變小時不能刪狀態 |
| `resolveAllSigningPositions`（全員會簽的位置判定） | 只有位置固定的關卡能會簽 |

產生器因此退化成「把同一份常數模板貼到目標 App」，`deployed_hash` 的意義也從
「路由改了沒重跑」變成「模板改版了這個 App 沒重新部署」。

**Jimmy 沒列到、但不處理就會靜默失效的一件事：全員會簽。**
ANY/ALL 是每個狀態靜態設定的，只有兩個簽核狀態的話會簽關卡無處可放。
補了第 7 個狀態 `會簽中`（type = ALL）解決——而且這樣**比原本更好**：
編號模型下全員會簽只能放在「位置固定」的關卡（前面不能有員工鏈段），現在放哪都行。

**自迴圈帶來的一個新歧義**：`會簽中 → 會簽中` 可能是「會簽還沒簽完」，也可能是
「這一關簽完了，下一關剛好也是會簽」——狀態轉移一模一樣，分辨不了。
（編號模型下 `簽核中(2) → 簽核中(2)` 沒有這個問題，因為推進一定會換號。）
解法是不看狀態，改看**簽名是否已覆蓋所有執行者**（`isFinalSignature`）。

**狀態不編號的代價**：filterCond 沒東西可看了——光看「簽核中」不知道下一站是主管、
經辦、會簽還是已簽完。所以多了兩個規約欄位 `next_state` / `reject_state`，
由 adapter 在**進入某一關時**就先算好下一步的去向（kintone 解析 filterCond 與
「指定欄位」執行者，用的都是按鈕按下**前**的值，這點與 §9.8 同源）。

**通則**：「不寫死」有兩個維度——名字與數量。名字統一了但數量仍隨資料變動的設計，
維護成本跟寫死差不多，因為每次資料變動都還是要回頭改設定。

**實測 PUT 又打出兩條官方文件沒寫的平台規則**（2026-09-01，App 737）：

| 錯誤訊息 | 規則 | 對策 |
|---------|------|------|
| 「初始狀態下，執行者的type只能指定為『ONE』。」 | index 0 的狀態 `assignee.type` 只能是 `ONE` | 草稿改 `ONE` |
| 「初始狀態下，執行者需為空、或指定為記錄的建立人欄位。」 | 初始狀態不接受 `CREATOR` 這個 entity type | 草稿執行者**留空**（kintone 預設範本也是如此）；可見範圍交給記錄權限管 |
| `actions[n].executableUser: ['此項必填。']` | `SECONDARY` 動作的 `executableUser` 必填 | 沒設可作廢群組時**直接不產生作廢動作**，而非給一個誰都能按的版本 |

兩條都補進 `validateStatusPayload`，之後 PUT 前就會擋下。

**這兩條都是「照文件寫、跑起來才知道錯」的類型。** 累積起來的模式很清楚：
kintone 流程管理 API 的文件只描述資料結構，不描述**約束**——
`ONE`/`ANY`/`ALL` 的語義、同名動作、自迴圈、初始狀態限制、SECONDARY 必填，
沒有一條寫在文件裡。這一層的規格只能靠實機打。所以產生器的 `validateStatusPayload`
才是這些知識的存放處：每打出一條就寫成一條驗證規則，下次不會再撞。
