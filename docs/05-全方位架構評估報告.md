## 結論

**方向是對的。** 「角色路由表 + 每個角色記下一關 + 跑到時才查是誰」這三件事，確實把組織異動隔離在資料裡，舊系統的那些寫法一個都沒出現。

做得好、要保持的地方：

- 建簽核鏈分三步：先走結構（只讀快取）、再一次平行查所有簽核者、最後組裝。5 關的鏈從約 1.5 秒降到 0.3 秒。
- 多個模組同時要載入角色表時，只會發一次 API。
- 循環偵測加上最大深度，兩道保險。
- 回傳格式統一是 `{ ok, chain, error }`，呼叫的人不用自己 try-catch。
- 代碼欄位全部對 HR 隱藏。

## 各項說明

### 1. 起點快取清不到（已修）

HR 改了某人的起點，那個人的頁面如果開著，送單時還是用舊的起點，整條鏈全錯。
修法：起點快取加上 60 秒過期，`ensureFresh()` 一次清角色和起點兩個快取，`buildChain` 也改成呼叫它。

### 2. 沒有簽核者還是能送單（已修）

群組被清空、或個人欄位被清掉，送單照樣成功，跑到那一關就卡住，沒有人收到警告。
修法：查完所有簽核者後檢查，有一關是空的就擋下來，說明是第幾關、哪個角色。

### 3. 子表格沒記簽核方式（已修）

角色表有「任一人簽／全員會簽」，但組簽核鏈時沒帶進子表格。趁子表格還沒放進任何申請 App 先補上，之後再改就要搬資料。

### 4. 同名角色設定不一致（已修）

同名的角色當成同一關，但如果兩筆的下一關設得不一樣，選同一個名字會走出兩條不同的鏈，畫面上看不出來。
修法：健康檢查加一條規則，同名角色的下一關、是否終點、簽核方式三項要一致。

### 5. 前端驗證可以被繞過

kintone 原生的檔案匯入、或直接用 API 寫入，都不會經過 JS 的檢查。這是 kintone 的限制，程式沒辦法擋。
對策寫進 HR 手冊：不要用原生匯入改這兩張表，要批量就用工具；每次批量改完跑一次健康檢查。

### 6. offset 分頁

80～200 筆角色完全沒問題。kintone 的 offset 上限是一萬，角色真的破千再改寫法。

### 7. 畫面客製可能被 kintone 更新弄壞

詳情頁卡片、編輯頁標題這些客製，依賴 kintone 內部的畫面結構。kintone 每月更新，哪天改了結構，功能會默默消失。
對策寫進 HR 手冊：每月更新後花 5 分鐘檢查幾個畫面，有異常就回報。

### 8. JS 沒載入時的畫面

JS 掛掉時，HR 會看到平常看不到的代碼欄位（例如 `ROLE_0095`），可能直接改出錯的資料。
對策寫進 HR 手冊：看到英文代碼欄位就停手，通知 IT。

### 9. 顯示名字時沒有統一跳脫（還沒處理）

流程預覽、詳情卡片、列表頁的簽核者欄，用 `innerHTML` 顯示角色名和人名時沒有跳脫。
目前這些名字都是 IT 維護的，風險很小，但哪天開放自訂名稱就會變成資安問題。
修法：`tools/04` 已經有 `_esc()`，搬到 `core/04-utils.js` 共用，四個地方統一用它。大約半小時。

位置：`apps/role-definition/04-chain-preview.js`、`05-detail-card.js`、`02-field-display.js`
