## 一、總評

**架構方向正確，核心決策經得起檢驗。** 「角色路由表 + Linked List + 跑到時才解析」三件事合起來，確實把組織異動完全隔離在資料層，舊系統的七大雷區（字串處理組織名、職稱 case、硬編碼特例…）在新程式碼中一個都沒有重蹈。

值得肯定的具體實作（不是客套，是逐檔看完的結論）：

| 項目 | 位置 | 評語 |
|------|------|------|
| 三階段平行化 buildChain | core/03-chain-builder.js:148 | 走結構（純快取）→ Promise.all 解析 holder → 純 CPU 組裝，5 關鏈從 1500ms 降到 300ms 的設計是教科書等級 |
| Promise singleton 防並發 | core/02-api-client.js:66 | 多模組同時觸發載入只發一次 API，且 finally 清 promise 讓失敗可重試 |
| visited Set 循環偵測 + MAX_DEPTH | core/03-chain-builder.js:94 | 雙保險，錯誤訊息還指出循環點 |
| 可搜尋分組下拉 + role_name 去重 | 03-next-role-dropdown.js / 01-entry-form-init.js | 80+ 角色的可用性問題解得乾淨 |

**但有三個缺口在 P8 試點前必須補**：起點快取無失效機制（#1）、空簽核者不擋（#2）、HR 操作手冊不存在（#11）。詳見下文。

## 二、後端評估

### #1 entryCache 無 TTL、forceFresh 清不到它 ｜ 嚴重度：🔴 中高

- **位置**：core/02-api-client.js:38（`entryCache` 宣告）、core/02-api-client.js:143（`ensureFreshRoles` 只清角色快取）
- **影響情境**：HR 把某員工的起點角色從「MIS－課員」改成「MIS－主任」。該員工的申請 App 頁面若已開著（或同一瀏覽器分頁曾查過），`getEntryRoleId()` 永遠回舊值——即使 submit 時帶了 `{forceFresh: true}`，因為 `ensureFreshRoles()` 只清 `roleCache`，不清 `entryCache`。**這會讓「保證資料最新」的 API 承諾落空**，且錯的是鏈的第一關，整條全錯。
- **建議修法**：`entryCache` 比照角色快取加 TTL（員工表按需查詢、單筆快取，TTL 可以更短，如 60 秒）；`ensureFreshRoles()` 改名或擴充為 `ensureFresh()`，同時清兩個快取。JSDoc 的 `@example` 一併更新。
- **建議時機**：P4 上傳前（此檔尚未上傳 kintone，不影響 P1 驗收）。

### #2 簽核者為空時 buildChain 仍回 ok:true ｜ 嚴重度：🔴 中高

- **位置**：core/03-chain-builder.js:50（`resolveHolders` 空群組/空個人回 `[]`）、core/03-chain-builder.js:165（Phase 2 之後不檢查空陣列）
- **影響情境**：IT 清空了某群組成員（或角色的 holder_user 被清掉但記錄仍啟用），申請人送單成功，鏈也寫進子表格，但某一關 `expected_signers` 是空的——流程跑到該關就卡死，而且**申請人與 HR 都不會收到任何警告**。健康檢查工具（tools/01）雖能事後掃出「空 holder」，但擋不住已送出的單。
- **建議修法**：Phase 2 解析完成後檢查 `holderLists`，任一關為空即回 `{ok: false, error: '第 N 關「角色名」目前沒有任何簽核者，請聯絡 HR'}`。這是 O(n) 一行 findIndex 的事，成本極低。
- **建議時機**：P4 上傳前。

### #3 approver_chain 子表格缺 signing_mode ｜ 嚴重度：🟠 中（設計缺口）

- **位置**：core/03-chain-builder.js:74（`assembleChainStep` 未帶入）、docs/02-欄位代碼對照表.md 子表格定義（無此欄）
- **影響情境**：角色表有 `signing_mode`（任一人簽/全員會簽），但鏈組裝時丟掉了。P8 整合原生流程管理時，每一關需要知道簽核模式才能決定行為（任一人簽 = 任一 expected_signer 按核准即推進；全員會簽 = 要等全部）。屆時要嘛回頭改子表格結構 + 重新產生既有記錄的鏈，要嘛每次 proceed 重查角色表（多一次 API 且有時間差問題）。
- **建議修法**：子表格加 `signing_mode` 欄（文字），`assembleChainStep` 帶入快照。**趁子表格還沒嵌入任何申請 App，現在改結構是零成本；上了 P8 之後再改是遷移工程。**
- **建議時機**：P8 開始前定案（搭配 docs/06 提案一起看，該提案對全員會簽有進一步的原生流程限制分析）。

### #4 同名角色去重 vs 單一 role_id 寫入的歧義 ｜ 嚴重度：🟠 中

- **位置**：設計決策見 docs/對話脈絡.md §9.2；健康檢查現有四規則見 tools/01-health-check.js:8-11（循環/斷鏈/孤立/空 holder，無同名一致性檢查）
- **影響情境**：下拉以 role_name 去重、把同名角色視為「同一關」，但記錄實際寫入的是其中一個 role_id。若兩筆同名角色的 `next_role_id` 不同（HR 手誤完全可能發生），同名去重的假設就破了：選同一個名字，走出兩條不同的鏈，而且 UI 上看不出來。
- **建議修法**：tools/01-health-check.js 加第 5 條規則「同名角色群組內 next_role_id / is_chain_end / signing_mode 必須一致」，不一致列為 🔴 級問題。
- **建議時機**：P5 上傳前（工具尚未上傳，順手加）。

### #5 所有驗證都在前端，REST API / CSV 匯入可繞過 ｜ 嚴重度：🟡 低中

- **位置**：全域性質（role_id 流水號產生、必填驗證、next_role_id 有效性全在 JS 層）
- **影響情境**：kintone 原生的檔案匯入、或任何拿到權限的人用 REST API 寫入，都不經過 JS 驗證。這是 kintone 平台的天生限制（無後端 hook），不是程式寫錯。
- **建議修法**：制度補位——(a) 操作手冊明文禁止 HR 用原生匯入功能改兩張表（要批量就用 tools/02-batch-import 的 dry-run 流程）；(b) 健康檢查訂為**每次批量異動後 + 每月一次**的例行動作；(c) App 權限收斂到最小集合（docs/02 的權限表已有規劃，實際上線時逐項核對）。
- **建議時機**：寫入 HR 操作手冊（見 #11）。

### #6 loadAllRoles 的 offset 分頁 ｜ 嚴重度：🟢 低（註記即可）

- **位置**：core/02-api-client.js:79
- **說明**：offset 分頁對 80~200 筆角色綽綽有餘。kintone 的 offset 上限 1 萬、深分頁會錯位，若未來角色數量破千再改 cursor 或 seek 法（`$id > last_id` 條件分頁）。現在不用動，留此註記防止未來誤判為疏漏。

## 三、前端評估

### #7 DOM 客製依賴 kintone 內部結構 ｜ 嚴重度：🟠 中（已接受的風險，需制度化）

- **位置**：apps/role-definition/05-detail-card.js（top-down DOM selector 移植原生 USER_SELECT 元素）、06-edit-layout.js（TreeWalker 改標題文字、解除 748px 寬限）
- **影響情境**：kintone 每月定期更新，原生 DOM 結構不在相容性保證範圍內。哪次更新改了 class 名或層級，卡片移植、標題改名就會靜默失效（safeHandler 會吞掉錯誤讓頁面不崩，但功能消失）。
- **建議修法**：不是改程式，是建制度——手冊附一頁「kintone 每月更新後的 5 分鐘冒煙檢查清單」：開一筆角色詳情頁看卡片、開編輯頁看分區標題與下拉、開清單頁看簽核者欄。任何一項異常就回報開發者。
- **建議時機**：寫入 HR 操作手冊（見 #11）。

### #8 JS 載入失敗時的 fallback 樣貌 ｜ 嚴重度：🟢 低

- **位置**：`next_role_id`（角色表）、`entry_role_id`（起點表）都是被 JS 隱藏的原始文字欄
- **影響情境**：指令碼掛掉（網路、CDN、上一條的 DOM 變動）時，HR 會看到裸的代碼欄位（如 `ROLE_0095`），可以直接改出髒資料。不會立刻壞（健康檢查抓得到），但要避免 HR 在異常畫面下繼續操作。
- **建議修法**：手冊訂「畫面異常就停手」原則——只要看到平常看不到的英文代碼欄位，一律停止編輯、通知 IT。
- **建議時機**：寫入 HR 操作手冊（見 #11）。

### #9 innerHTML 未統一 escape ｜ 嚴重度：🟢 低（順手修）

- **位置**：apps/role-definition/04-chain-preview.js:232、04-chain-preview.js:424（tooltip 與 Timeline 渲染角色名/成員姓名）、05-detail-card.js:275（卡片渲染）、02-field-display.js:137（清單頁簽核者欄）
- **影響情境**：插值內容是角色名（計算欄位，來源為 IT 維護的下拉選項）與使用者/群組顯示名（cybozu 後台，IT 維護），攻擊面實際上很小。但「來源目前可信」不等於「永遠可信」——哪天顯示名開放自訂就變成 stored XSS。
- **建議修法**：tools/04-batch-role-creator.js 已經有 `_esc()`，把它抽到 core/04-utils.js 共用，四個檔案的插值統一過一層。半小時的工。
- **建議時機**：P4/P5 上傳前順手一併處理（會動到 P1 已上傳的檔案，等驗收簽收後再上）。

### #10 UI 整體評價

35-55 歲使用者原則貫徹得很好：可搜尋下拉（打字或用滑）、Timeline 圓點視覺、hover 看成員姓名、SweetAlert 大字提示、代碼全隱藏。行動版依 Q7 決策只做唯讀顯示，hover tooltip 在行動版沒有對應互動屬已知取捨，不列缺陷。

## 四、操作文件與維運評估

### #11 HR 操作手冊不存在，但 HR 已在真實 App 上操作 ｜ 嚴重度：🔴 中高

- **現況**：`docs/01-HR維護操作手冊.md` 排在 P10 定稿，目前連草稿都沒有。但 App 685 已上真實資料、HR 介面已在使用，「規格書提到的『HR 維護介面用 kintone 預覽會掉資料，文件強調禁用預覽』」這條救命警告目前只存在於風險表裡，HR 看不到。
- **建議**：提前產出**快速上手版**（2-3 頁就夠），涵蓋：新增/修改角色 SOP、設定員工起點 SOP、**禁用預覽功能警告**、批量匯入的 dry-run 流程、健康檢查怎麼跑怎麼看、#7 的每月冒煙檢查清單、#8 的「畫面異常就停手」原則。P10 再擴充成完整版。
- **建議時機**：P2 上傳前後（HR 開始操作起點表之前）。

### #12 應變指南建議提前出綱要 ｜ 嚴重度：🟠 中

- **現況**：`docs/03-應變指南.md` 排在 P9。
- **建議**：不用等 P9 寫全文，先出一頁綱要，至少回答三題：(a) 試點切換失敗怎麼回退舊系統；(b) IT 誤刪群組/清空成員，在途單怎麼救（與 #2 直接相關）；(c) 角色被停用時，已寫入該 role_id 的在途單如何處理。這三題的答案會反過來影響 P8 adapter 的設計，早想比晚想便宜。

### 文件整體

`對話脈絡.md` 的「記錄為什麼」做法是本專案最有價值的資產之一，接手成本極低，請維持。`Phase進度追蹤.md` 與實際程式碼狀態一致（逐項抽查過）。規格書 1.1 版與現況的差異只有 §9 變更履歷未記到 5、6 月的迭代，屬小事。
