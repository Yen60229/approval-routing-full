# Approval Routing Engine — 簽核路由引擎規格書

> 版本 1.0 ｜ 建立日期 2026-04-13 ｜ 作者 Jimmy + Claude

---

## 1. 專案目標

取代舊有「組織名稱 + 職稱」推導簽核者的設計，改用**資料驅動的角色路由表**，讓組織異動完全脫離程式碼。

| 維度 | 設定 |
|------|------|
| 定位 | 可重複使用的核心模組，所有 App 接入只需 4 行程式碼 |
| 試點策略 | 一步到位取代舊系統，但保留 P8 試跑階段降低風險 |
| 人員機制 | 混合（重要角色用 GROUP_SELECT、其餘用 USER_SELECT） |
| 稽核方式 | 由各 App 既有「簽核記錄外掛」負責，本系統不重複實作 |
| 裝置 | 電腦版完整功能、行動版唯讀顯示 |
| 規模 | 500+ 員工、80+ 角色 |

---

## 2. 核心設計理念

### 2.1 不再做的事
- ❌ 用組織名稱字串處理推導職稱（`processOrgName()` 完全廢棄）
- ❌ 用 `case '課長'/'次長'/'部長'` 寫死職稱判斷
- ❌ 用 `SPECIAL_DEPARTMENTS` 硬編碼陣列處理特例
- ❌ 多次呼叫 `kintone.app.record.get()`（一次 get、最後 set）

### 2.2 改用的設計
- ✅ Linked List 結構表達簽核鏈（each role has a `next_role_id`）
- ✅ 角色抽象層解耦員工與簽核者（員工只知道「下一關角色」、不知道「下一關是誰」）
- ✅ GROUP_SELECT 讓 IT 後台改群組成員即可全局生效
- ✅ Strategy Pattern 替代 if-else
- ✅ Cache Map 避免重複 API 呼叫
- ✅ 所有事件統一 `safeHandler` 包裹

## 3. 系統架構

### 3.1 三層架構

```
┌─ 維護層 ─────────────────────────────────────┐
│  IT 部門：維護 kintone 群組成員              │
│  HR 部門：維護角色定義表 + 員工起點對照表    │
└──────────────────────────────────────────────┘
                    ↓
┌─ 資料層 ─────────────────────────────────────┐
│  App 1: role_definition  (~80 筆)            │
│  App 2: employee_entry   (~500 筆)           │
│  共用子表格: approver_chain (嵌入各申請 App) │
└──────────────────────────────────────────────┘
                    ↓
┌─ 引擎層 ─────────────────────────────────────┐
│  window.ApprovalRouting.ApprovalEngine       │
│  - buildChain()       建構簽核鏈             │
│  - validateChain()    驗證鏈完整性           │
│  - simulateChain()    模擬產生（不寫入）     │
│  - reverseQuery()     反向查詢               │
└──────────────────────────────────────────────┘
                    ↓
┌─ 應用層 ─────────────────────────────────────┐
│  各申請 App（採購、請假、出差、...）         │
│  接入只需 4 行程式碼                         │
└──────────────────────────────────────────────┘
```

### 3.2 簽核者解析時機

| 時間點 | 動作 | 結果 |
|--------|------|------|
| 申請人按儲存 | 沿著鏈走，把每關的「角色 ID」存進子表格 | 子表格存的是角色 |
| 流程跑到第 N 關 | 即時查角色目前的 holder（群組或個人） | **跑到時才知道是誰** |
| 中間群組換人 | IT 改群組 → 後續所有單都用新人 | 舊單在下一關自動切換 |

## 5. 開發紀律

### 5.1 沿用既有 Pattern Library 風格
- IIFE 包裹所有檔案（防全域變數污染）
- `const` + `Object.freeze(CONFIG)` 集中設定
- `async/await`（不用 callback）
- `safeHandler()` 統一錯誤處理 + SweetAlert
- 事件用 `events.flatMap()` 一次綁 create/edit/mobile

### 5.2 命名規範

| 用途 | 規則 | 範例 |
|------|------|------|
| 主鍵 ID | 簡短英文 | `role_id`, `employee_code` |
| 顯示名稱 | `*_name` | `role_name`, `display_name` |
| USER_SELECT | 動詞或角色 | `applicant`, `holder_user` |
| GROUP_SELECT | `*_group` | `holder_group` |
| 關聯 ID | `*_id` | `next_role_id`, `entry_role_id` |
| 布林 | `is_*` | `is_active`, `is_chain_end` |
| 時間 | `*_at` / `*_date` | `signed_at` |
| 子表格 | 名詞複數 | `approver_chain` |

## 8. 風險與緩解

| 風險 | 緩解 |
|------|------|
| `kintone.getMembersByGroupCode()` 在私有部署可能不存在 | P0 前由 IT 確認 |
| 80+ 角色 + 鏈深度 5+，編輯頁預覽會卡 | P3 加快取 |
| 500+ 員工批量匯入失敗 | P2 加 dry-run 模式 |
| 一步到位切換有風險 | P8 試跑 2 週 + P9 應變指南 |
| HR 維護介面用 kintone 預覽會掉資料 | 文件強調，禁用預覽 |
