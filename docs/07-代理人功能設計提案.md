# 07 — 代理人功能設計提案

> 版本 1.0 ｜ 建立日期 2026-07-06 ｜ 作者 Jimmy + Claude
> 需求原文：較高層級能代理較低層級即可，同仁不用都告知 IT 修改，可以自己跑需求單、較高層級主管核可後就更改人員；代理結束或同仁休假回來，要再自行回來報到更換回原本的人員。
> **已確認的決策（2026-07-06）：代理期間原簽核者與代理人並列皆可簽。**
> **依賴：docs/06 的 adapter 規約**（代理生效點掛在 process.proceed 的解析時機），故排程在表單路由之後。

---

## 一、設計原則：代理是「解析層的 overlay」，不是改資料

本引擎的核心語義是「跑到時才解析簽核者」。代理人正好搭同一班車：**不改角色表、不改群組、不改任何在途單**，只在每次解析 holder 的當下，多套一層代理對照。

```
resolveHolders(角色) → [原簽核者們]
        ↓ 套 delegation overlay
[原簽核者們] ∪ [其中有人正在被代理 → 加上其代理人]   ← 並列皆可簽
```

這個做法的直接好處：

| 好處 | 說明 |
|------|------|
| 到期自動失效 | kintone 沒有排程器，但引擎每次解析都用「今天」判斷生效區間——代理人**忘記解除也不會殘留權限**。「同仁回來自行報到解除」保留為提前結束的手段，不是唯一防線 |
| 在途單即時生效 | 代理核可的下一關開始就套用，不用回頭改任何已送出的單 |
| 零資料汙染 | 角色表、群組、approver_chain 全部不動；代理結束後系統狀態自然回復，沒有「換回來」的資料操作 |

## 二、新 App：代理設定表 `delegation`

**App ID：待建立後補**（寫入 core/01-config.js）

| # | 欄位代碼 | 顯示名稱 | 類型 | 必填 | 說明 |
|:-:|---------|---------|------|:----:|------|
| 1 | `principal_user` | 被代理人 | 使用者選擇（單選） | ✓ | 休假/出差的同仁 |
| 2 | `delegate_user` | 代理人 | 使用者選擇（單選） | ✓ | 接手簽核的人 |
| 3 | `start_date` | 代理開始日 | 日期 | ✓ | 含當日 |
| 4 | `end_date` | 代理結束日 | 日期 | ✓ | 含當日；引擎以「今天 ∈ [start, end]」判斷生效 |
| 5 | `scope` | 代理範圍 | 單選按鈕 | ✓ | v1 固定「全部表單」；欄位先建，未來擴充「指定表單」不用改表 |
| 6 | `reason` | 事由 | 文字（多行） | | 給核可主管看的 |

**不需要 `is_active` 欄**——生效與否由「流程狀態 = 已核可」+「日期區間」共同決定，避免兩套開關互相矛盾。

### 核可流程：用 kintone 原生流程管理，一關搞定

```
申請中 ──主管核可──→ 已核可 ──（同仁回來）提前結束──→ 已結束
   └──────撤回────→ 已撤回
```

- 這張表自己的簽核**不吃自家引擎**（一關而已，用引擎是循環依賴 + 殺雞用牛刀），處理人直接設較高層級主管的群組。
- 「提前結束」動作開放給 principal_user 與 delegate_user 本人執行（executableUser），對應需求裡「自行回來報到更換回原本的人員」——差別是在本設計中這是**提前結束**，不做也會在 end_date 自動失效。

## 三、層級驗證：較高層級代理較低層級

驗證邏輯（submit 時）：

1. 層級序 = 角色表 `title_level` 下拉選項的**排列順序**（IT 在後台維護順序，程式以 `getFormFields()` 動態載入——沿用 9.1 的既有做法，不硬編碼）。
2. 反查 role_definition：principal / delegate 各自作為 holder（個人指定或群組成員）出現在哪些角色，取其最高 title_level。
3. 驗證 `delegate 層級 ≥ principal 層級`，不符即 event.error 擋下。

**明列的取捨**：delegate 可能不在任何角色中（例如新任主管尚未進群組），此時反查不到層級——**放行，以「較高層級主管核可」作為主要防線**，層級驗證定位為盡力而為的第一道網。理由：把驗證做死會讓例外情境（組織過渡期）反而要找 IT，違背這個功能「不用告知 IT」的初衷。

## 四、引擎整合

```
ApiClient 新增：
  getActiveDelegations()
    → Map<principalCode, delegateCode>
    查詢條件：流程狀態 = 已核可 and start_date <= 今天 <= end_date
    快取 TTL：60 秒（代理筆數少、變動頻率低，但生效延遲要短）

ChainBuilder / adapter 共用：
  applyDelegation(holders)
    → holders ∪ holders.map(對照表).filter(Boolean)   // 並列，去重
```

套用點有兩處，語義不同：

| 套用點 | 目的 |
|--------|------|
| adapter 的 process.proceed 寫 `current_approvers` 時（docs/06 §5.3） | **決定性的一點**——真正控制誰能簽 |
| buildChain 的 Phase 2 之後（expected_signers 顯示） | 透明度——讓申請人在子表格上看得到「這關目前含代理人」 |

複雜度：O(關卡數 × 每關人數) 的 Map 查找，可忽略。

## 五、操作流程（使用者視角）

```
同仁要休假
  → 開代理設定表，填被代理人/代理人/起訖日/事由，送出     （自己跑需求單 ✓）
  → 較高層級主管在 kintone 收到待處理，按「主管核可」        （主管核可後生效 ✓）
  → 期間內：所有輪到被代理人的關卡，代理人並列出現、皆可簽
  → 提前回來：本人或代理人按「提前結束」                     （自行報到解除 ✓）
  → 或什麼都不做：end_date 過後自動失效                      （忘了也不會出事 ✓）
```

HR/IT 全程不用介入。手冊（docs/01）屆時補一頁本流程的圖文版。

## 六、風險與待決點

| 項目 | 說明 | 處理 |
|------|------|------|
| 代理鏈（A 代理 B，A 又休假由 C 代理） | overlay 只套一層，C 不會自動繼承 B 的關卡 | v1 明文不支援（實務罕見）；監測需求再議 |
| 同一 principal 重疊區間多筆代理 | 兩個代理人同時生效 | 允許（並列模式天然相容），submit 時提示重疊即可 |
| 代理人本來就在同一關（群組成員） | 去重後無感 | 無需處理 |
| 已到該關、代理才核可 | 該關的 current_approvers 已寫入，不會回頭補 | 待決點：v1 接受（下一關起生效）；若要立即生效需掃在途單回寫，成本高，不建議先做 |

## 七、建議排程

P8 試點（含 docs/06 adapter）跑穩之後再實作——代理的 overlay 是掛在 adapter 的解析點上運作的，adapter 若還沒上線，代理功能就沒有地方可以掛載、無從生效。預估工作量：建表 + 表單 JS（層級驗證）+ ApiClient/adapter 整合，約 1-2 次會話。
