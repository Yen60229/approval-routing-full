## 二、盤點時發現的三件事

1. **只有 08、09、11 有 App ID 守門**（`kintone.app.getId()` 比對）。
   其餘 8 支是「上傳到哪就長在哪」，完全靠上傳清單人工控制，貼錯 App 就會冒出不該有的按鈕。
2. **重複打 API**：01、05、06、08、11 各自全量拉一次 685（部分還加上使用者／組織 API），
   開三個工具就打三輪。
3. **資料抓取原本重複實作**：後台使用者／組織／職務與 `unit_name`／`title_level` 對應，
   05 與 11 都要用 → 2026-09-01 已抽成 `core/08-directory.js`，兩邊共用同一份規則。

## 三、分組建議（3 顆 ＋ 1 顆）

依「HR 當下想做什麼」分組，而不是依檔案編號：

| 群組 | 收哪些 | 為什麼收在一起 |
|------|-------|--------------|
| **體檢** | 01 健康檢查、05 未設定名單、06 簽核者重複檢查、09 role_id 位數對照、11 人事異動對照 | 互動一模一樣（掃描→列問題→勾選→批次寫回），而且資料來源大量重疊，合併後只要拉一次 |
| **查詢** | 02 模擬器、03 反向查詢、08 查簽核鏈 | 全部唯讀，都是「輸入一個關鍵字 → 看一條鏈」 |
| **維護** | 04 批次角色建立、07 批次設定下一關 | 主動性的大量寫入作業，不是從問題清單出發 |
| **（獨立）** | 10 部署流程設定 | 只掛 736、只在部署時用，與上面三群沒有交集 |

## 四、實作建議：做容器，不要真的合併

八支工具合計約 8,000 行，硬合併風險高、效益低。建議加一層薄薄的註冊表：

```
core/09-tool-registry.js
  registerTool({ group: '體檢', label: '健康檢查', apps: [685], run })
  → 依 group 產生 3 顆按鈕，點開是下拉選單
  → 統一守門 App ID（解決發現 1）
  → 共用一份角色／使用者快取（解決發現 2）
```

各工具本體幾乎不動，只把最後那段「建立按鈕、appendChild」換成 `registerTool(...)`。

**尚未動工**，等 Jimmy 決定要不要做（P8 端到端測試完再排比較安全）。
