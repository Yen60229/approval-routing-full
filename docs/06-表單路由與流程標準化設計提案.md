# 表單路由與流程標準化

公司有 40～50 張電子表單，而且會越來越多。這份說明怎麼讓每張表單走自己的簽核流程，又不用每張表單各寫一套程式。

- 狀態：**設計定案，程式已完成，等 kintone 實測**
- 版本 2.0（2026-09-01）
- 欄位的完整定義以 `02-欄位代碼對照表.md` 為準，這份只講設計和理由

---

## 一、為什麼要多一張表

685、686 回答的是「**這個人**送單，會經過誰」，但回答不了「**這張單**要走哪些關卡」。

請假單簽到部長就結束；採購單還要經過會計經辦、總務部長。同一個申請人，不同表單，流程不一樣。

其他做法都不好：

| 做法 | 問題 |
|------|------|
| 每個申請 App 的程式裡寫死自己的加簽關卡 | 40～50 份程式各寫各的，改流程又要改程式 |
| 角色表加一欄「適用哪些表單」 | 角色和表單是多對多，80 筆角色會變成幾百筆 |
| 每種表單建一套自己的角色鏈 | 同一個課長在 50 條鏈裡重複 50 次，換人要改 50 筆 |

所以多加一張表（App 736）：**表單 → 路由設定 → 角色**，跟「員工 → 起點角色 → 人」是同一個想法。

---

## 二、一條簽核鏈 = 幾段拼起來

看實際的關卡（主管、次長、部長、會計經辦、總務經辦、總務部長），可以分成兩類：

```
員工鏈段（因人而異）                     指定角色段（因表單而異）
起點 → 課長 → 次長 → 部長        →      會計經辦 → 總務經辦 → 總務部長
沿 685 往上走，走到某個職稱就停           直接指定角色，跟申請人無關
```

- **員工鏈段**：沿著申請人的起點往上走，用 685 現有的 `title_level` 決定停在哪，角色表不用改。
- **指定角色段**：直接指定某個角色。角色換人照樣在 685 或群組改，這裡只記是哪個角色。

一條路由由幾段依序組成，段數和順序都不限，例如「員工鏈簽到課長 → 會計經辦 → 員工鏈簽到部長」。

### 2.1 簽到哪裡停、哪幾層跳過

員工鏈段有兩個設定：

```
簽到哪個職稱為止 = 部長     → 走到部長就停（部長要簽）
跳過的職稱       = [次長]   → 路上遇到次長不用簽
結果：起點 → 課長 → （次長跳過）→ 部長
```

跳過的關卡照樣沿著下一關往下走，只是不列入簽核名單，所以不會斷掉。

### 2.2 兩個特別情況

| 情況 | 怎麼處理 |
|------|---------|
| 連續兩關剛好是同一個人（例如課長兼會計經辦） | 兩關都留，簽核軌跡比較清楚 |
| 部長自己送單，設定是「簽到部長為止」 | 員工鏈段為空，主管不用簽自己的單 |

### 2.3 沒設定的表單

736 裡找不到這張表單，或沒勾啟用，就照原本的方式：從申請人的起點一路走到終點。已經接好的 App 不受影響。

## 三、App 736 由誰維護

由 **IT 或各表單窗口**維護，不是 HR。HR 管人和角色，表單窗口管單據怎麼走。
因為使用者不是 HR，這張表的角色代碼欄位不用藏起來。

## 四、引擎

```
buildChainForForm(員工帳號, 表單 App ID, 選項)
  → { ok, chain, error }      // 跟 buildChain 一樣的回傳格式
```

1. 讀 736 的路由設定（快取 5 分鐘）
2. 一段一段展開：員工鏈段沿著 685 走、指定角色段直接取角色
3. 每一關查現在是誰（平行查）
4. 組成子表格的內容

走過的角色會記下來，就算跨段也能抓到繞圈。某一關查不到簽核者，直接回錯誤，告訴你是第幾關。

## 五、流程管理：每張表單都一樣

### 5.1 固定 7 個狀態

```
草稿 ─送出→ 簽核中 ⇄ 經辦人確認中 ⇄ 會簽中 ─同意→ 核決
               │    （可以自己連回自己）
               └─駁回→ 駁回 ─再申請→ 草稿
（還沒結束的狀態都可以「作廢」，只限指定的群組按）
```

| 狀態 | 執行者 | 用在哪 |
|------|--------|--------|
| 草稿 | 不設 | 申請人編輯 |
| 簽核中 | `current_approvers`，任一人 | 員工鏈段的關卡 |
| 經辦人確認中 | `current_approvers`，任一人 | 指定角色段的關卡 |
| 會簽中 | `current_approvers`，全員 | 要全員會簽的關卡 |
| 駁回 | 申請人 | 改完再申請 |
| 核決 | 無 | 結束 |
| 作廢 | 無 | 結束 |

簽核者只會看到「同意」和「駁回」兩顆按鈕。

狀態名稱不綁職稱，也不帶關卡編號。「簽核中」和「經辦人確認中」分的是工作性質（主管或經辦），不是組織位置。

### 5.2 關卡數不同怎麼辦：狀態自己迴圈

課員送單可能 5 關，部長送單可能 2 關。kintone 允許「簽核中 → 簽核中」這種自己連回自己的動作（Jimmy 2026-09-01 實際測過），
所以 5 關就在「簽核中」上迴圈 5 次，每次換一個執行者。

要往哪裡走，看記錄上的 `next_state`：

```
簽核中 ─同意（next_state = 簽核中）       → 簽核中         下一關還是主管
簽核中 ─同意（next_state = 經辦人確認中）  → 經辦人確認中    下一關是經辦
簽核中 ─同意（next_state = 會簽中）        → 會簽中         下一關要會簽
簽核中 ─同意（next_state = 核決）          → 核決           沒有下一關了
```

三個簽核狀態各 4 條，一共 12 條「同意」，名字都一樣，簽核者只看到一顆按鈕。「駁回」也一樣，看 `reject_state`。

這樣做的好處：

- 每個申請 App 的流程設定一字不差
- 組織多一層主管，流程設定不用動
- 關卡數沒有上限
- 全員會簽放在哪一關都可以

### 5.3 全員會簽為什麼要有自己的狀態

kintone 的「任一人」或「全員」是每個狀態固定的，不能每張單不同。
「簽核中」和「經辦人確認中」是給任一人簽的關卡共用的，所以全員會簽的關卡要停在「會簽中」。

每一關停在哪個狀態，送單時就決定好，記在子表格的 `step_state`：
員工鏈段 → 簽核中、指定角色段 → 經辦人確認中，全員會簽的一律 → 會簽中。

### 5.4 文件沒寫、實際部署才知道的規則

| 規則 | 怎麼處理 |
|------|---------|
| 第一個狀態的執行者類型只能是 `ONE` | 草稿用 `ONE` |
| 第一個狀態的執行者只能留空或用建立者欄位，不接受 `CREATOR` | 草稿的執行者留空，誰看得到由記錄權限決定 |
| 次要動作（作廢）一定要指定誰能按 | 沒設「可作廢群組」就不產生作廢動作 |
| 有單子停在上面的狀態不能刪，刪掉的名字也不能再用 | 從舊的編號流程換過來時要注意，產生器會先掃出來提醒 |
| 任一人是 `ANY`，`ONE` 是「指定其中一人」 | 照正確的值寫 |
| 使用者欄位當執行者要用 `FIELD_ENTITY` | 照正確的值寫 |

這些都寫進產生器的檢查（`validateStatusPayload`），部署前會先擋下來。

## 六、標準 adapter

一支 `adapters/00-standard-adapter.js` 掛在所有申請 App 上，不認得任何特定表單。

### 6.1 申請 App 要加的欄位

`approver_chain`（子表格）、`current_approvers`、`current_step`、`total_steps`、`next_state`、`reject_state`，共 6 個。
型別看 `02-欄位代碼對照表.md`。

### 6.2 執行者怎麼設

在核准事件裡改 `current_approvers` 欄位，kintone 不一定會採用（它看的是按下按鈕前的值）。所以：

- **用「更新執行者 API」為準**：[`PUT /k/v1/record/assignees`](https://cybozu.dev/ja/kintone/docs/rest-api/records/update-assignees/)，以登入者身分呼叫，不需要 API token。
- 流程管理的執行者還是設「指定欄位 → `current_approvers`」，當作備用。更新執行者 API 只能在狀態已經有設執行者時使用。

### 6.3 adapter 在什麼時候做什麼

**存檔（草稿）**
- 重新抓最新資料，依路由算出整條簽核鏈
- 寫入子表格、總關卡數，`current_step` 設 0（0 代表還沒開始簽）
- 先把第 1 關的人寫進 `current_approvers`，因為 kintone 看的是按下「送出」之前的值
- 只有草稿才重算，已經在跑的單不重算

**按下流程按鈕**
- 看「下一個狀態」決定要不要往下走，**不是**按一次就往下一關
- 全員會簽的關卡，每個人按都會觸發事件，但狀態不變，這時只記簽名
- 會簽中 → 會簽中 可能是「還沒簽完」，也可能是「下一關剛好也是會簽」，所以看「是不是所有人都簽了」
- 往下走時，即時查下一關是誰，並先算好下一步的 `next_state`、`reject_state`
- 兩個人同時按時，`current_step` 對不上就擋下來

**打開詳情頁（補正）**
- 即時查這一關現在該是誰，跟實際的執行者比
- 不一樣就呼叫更新執行者 API（帶 `revision`，衝突就重讀再試一次），然後重新整理頁面
- 比對的是即時查到的人，不是送單時記下的名單。這樣「事件沒生效」和「HR 換人了」都補得到
- 連續兩次補不成功就停下來，提示找 IT，不會一直重整

### 6.4 權限

adapter 要寫欄位，所以簽核者要有記錄的編輯權限。做法：記錄權限依狀態開放給簽核者，再用 JS 把業務欄位鎖住。

- kintone 的欄位權限不能依狀態切換，擋不住有人故意用 API 改單，但那是舞弊，變更履歷查得到。
- **API token 不能寫在前端 JS**。目前也沒有 kintone 以外的執行環境，所以一律用登入者身分呼叫 API。

## 七、部署流程（tools/10 產生器）

在 736 的列表頁按「部署流程設定」：

```
1. 讀目前的流程設定，先備份（可以下載成檔案）
2. 產生標準的 7 個狀態（唯一會變的是「可作廢群組」）
3. 檢查（5.4 那些規則、狀態都存在、同名動作條件不重疊等）
4. 寫到測試環境（帶 revision，避免蓋掉別人改的）
5. 人工到 kintone 畫面確認
6. 正式部署
7. 回寫部署時間和版本（deployed_at、deployed_hash）
```

`deployed_hash` 用來看「標準流程改版了，這個 App 還沒重新部署」。

**新表單接進來的步驟**：在 736 建一筆路由 → 申請 App 加 6 個欄位 → 掛 adapter → 跑一次產生器。
原本每張表單要手動設定半天，現在大約十分鐘。詳細步驟看 `09-表單接入與測試手冊.md`。

## 八、三張表的關係

```
員工 → 686 員工起點對照表 → 起點角色             HR 維護
角色 → 685 角色定義表     → 是誰、下一關是誰      HR 維護
表單 → 736 表單路由設定表 → 走哪幾段              IT／表單窗口維護
                  ↓
        buildChainForForm()
                  ↓
   各申請 App（adapter + 6 個欄位 + 標準流程）
```

組織異動改 685、686，流程改版改 736，都不用動程式。

## 九、風險

| 風險 | 怎麼處理 |
|------|---------|
| 簽核者要有記錄編輯權限 | 依狀態開放 + JS 鎖欄位（6.4） |
| 兩個人同時按同意 | 檢查 `current_step`，對不上就擋；更新執行者 API 帶 revision |
| 執行者沒換成功 | 詳情頁補正（6.3） |
| 產生器蓋掉別人手動改的流程 | 帶 revision，部署前先備份 |
| 指定的角色被停用 | 建鏈時就回錯誤 |
| 以後要依金額走不同流程 | kintone 的分歧條件本來就能看數字，架構不用改 |
