# 06 — 表單路由與流程標準化設計提案

> 版本 1.0 ｜ 建立日期 2026-07-06 ｜ 作者 Jimmy + Claude
> 回答的問題：「公司有 4-50 個電子表單且只會更多，是否再多一個 App 來設定各表單簽核跑的順序，搭配兩張表實現更完整的自動化簽核？」
> **結論：是，建議新增第三個 App。** 且此設計把 backlog 的「#5 不同申請類型走不同鏈（v2）」與「#14 整合原生流程管理（P8）」一次收斂。

---

## 一、為什麼需要第三張表

現行兩張表回答了「**這個人**送單，鏈長什麼樣」，但回答不了「**這張單**該走哪條鏈」。請假單簽到部長就結束、採購單要多走會計經辦與總務部長、費用報支可能要會計經理——同一個申請人，不同表單，鏈不同。

不加表的替代方案都不及格：

| 替代方案 | 為什麼不行 |
|---------|-----------|
| 每個申請 App 的 adapter 裡寫死自己的加簽關卡 | 40-50 份 adapter 各自為政，回到「改流程要改程式」的老路，違反本專案存在的理由 |
| 角色表加「適用表單」欄位 | 角色與表單是多對多，塞進角色表會讓 80 筆角色爆炸成數百筆組合 |
| 每種表單建一套獨立的角色鏈 | 「MIS－課長」在 50 條鏈裡重複 50 次，換人要改 50 筆，違反 DRY——這正是階段 1 被否定的原因，只是換個維度重犯 |

**正解與本專案一路以來的哲學一致：再加一層 indirection。** 表單 → 路由設定 → 角色，正如員工 → 起點角色 → 人。

---

## 二、核心洞察：任何申請單的鏈 = 個人段 + 職能段

觀察 Jimmy 列出的標準關卡（主管／次長／部長／會計經辦人／總務經辦人／總務部長），它們天然分成兩類：

```
┌─ 個人段（因人而異）─────────────┐  ┌─ 職能段（因表單而異，固定）──────┐
│ 起點角色 → 課長 → 次長 → 部長    │→│ 會計經辦 → 總務經辦 → 總務部長    │
│ （沿現有 Linked List 往上走，    │  │ （固定的角色序列，直接指定        │
│   走到指定職稱層級即停）         │  │   role_id，與申請人無關）        │
└─────────────────────────────────┘  └─────────────────────────────────┘
```

- **個人段**：完全複用現有兩張表。截止點用角色表**已有的 `title_level` 欄位**表達（「沿申請人的鏈走，遇到第一個 title_level =『部長』的角色即停」），**不需要改角色表結構**。
- **職能段**：固定角色序列，逐關指定 role_id。角色換人依然走角色表/群組，這裡只存「哪個角色」。

一條路由 = 若干段的有序拼接。最常見的形態是「一個個人段 + 零到多個職能關卡」，但模型不限制段數與順序（例如純職能流程可以完全沒有個人段）。

## 三、新 App：表單路由設定表 `form_route_config`

**App ID：待建立後補**（比照 685/686 寫入 core/01-config.js）

| # | 欄位代碼 | 顯示名稱 | 類型 | 必填 | 唯一鍵 | 說明 |
|:-:|---------|---------|------|:----:|:------:|------|
| 1 | `form_app_id` | 表單 App ID | 數值 | ✓ | ✓ | 申請 App 的 kintone App ID，adapter 以此查路由 |
| 2 | `form_name` | 表單名稱 | 文字（單行） | ✓ | | 例：「採購申請單」，給維護者看的 |
| 3 | `is_active` | 啟用狀態 | 核取方塊 | | | 選項「啟用中」，比照兩表慣例 |
| 4 | `route_steps` | 路由關卡 | 子表格 | ✓ | | 有序，見下 |

子表格 `route_steps`：

| 欄位代碼 | 顯示名稱 | 類型 | 說明 |
|---------|---------|------|------|
| `step_no` | 順序 | 數值 | 段的執行順序 |
| `segment_type` | 段類型 | 單選按鈕 | 選項：`員工鏈段` / `指定角色段` |
| `stop_at_title_level` | 簽到職稱為止 | 下拉式選單 | 員工鏈段專用；選項與角色表 `title_level` 同一組（IT 維護，程式以 `getFormFields()` 動態載入，沿用 9.1 的做法） |
| `role_id` | 指定角色 | 文字（單行） | 指定角色段專用；由程式提供**現有的可搜尋分組下拉元件**（03-next-role-dropdown.js 抽共用），HR/窗口看到的是 role_name |

UI 沿用既有紀律：`role_id` 對維護者隱藏、`segment_type` 切換時條件顯示對應欄位（P7 pattern）、送出時驗證段類型與欄位的配對完整。

**維護分工**：此表由 **IT 或各表單窗口**維護，不是 HR——HR 管「人與角色」，表單窗口管「單據走什麼流程」，職責切開。權限表比照兩表模式另訂。

## 四、引擎 v2 API

```
buildChainForForm(employeeCode, formAppId, options)
  → { ok, chain, error }        // 契約與 buildChain 完全相同
```

行為規格：

1. 查 `form_route_config`（快取，TTL 比照角色表 5 分鐘）：
   - **查無該表單或未啟用 → fallback 走現行 `buildChain()` 全鏈**。既有規劃完全不受影響，已接入的 App 一行都不用改，向下相容。
2. 逐段展開：
   - `員工鏈段`：沿申請人起點角色走 Linked List，走到第一個 `title_level` = `stop_at_title_level` 的角色**（含該角色）**即停；走到 `is_chain_end` 仍沒遇到 → 回 `{ok: false, error}`（設定矛盾，讓維護者立刻知道）。
   - `指定角色段`：直接取該 role_id 的角色記錄。
3. 全部段拼接後，統一走現行 Phase 2（Promise.all 解析 holder）與 Phase 3（組裝子表格）——**這兩階段程式碼原封不動複用**。
4. 循環偵測：visited Set 涵蓋跨段（防止職能段又指回個人段造成重複）。

**待決點（實作前跟 Jimmy 確認）**：

| 待決點 | 選項 | 傾向 |
|--------|------|------|
| 連續兩關解析出同一人（如課長兼會計經辦） | 保留兩關 / 自動合併為一關 | 傾向保留兩關（單純、留簽核軌跡），試點看實際感受再說 |
| 個人段起點就是截止職稱（部長自己送單） | 個人段為空直接進職能段 / 至少含本人一關 | 傾向個人段為空（主管送單不用簽自己） |

## 五、流程管理標準化（40-50 個表單的一致性）

### 5.1 狀態命名模板（全公司統一）

```
草稿 → 簽核中(1) → 簽核中(2) → … → 簽核中(K) → 核准
        │                                  ├→ 駁回（處理人=申請人，可再申請回草稿）
        └──────────（每個非終態掛「作廢」SECONDARY 動作，限定群組）
```

- K = 該表單路由的**最大可能深度**（個人段最深 + 職能段長度），由產生器計算，上限建議 10。
- 狀態名是「簽核中(n)」而不是「課長審核中」——**狀態名絕不綁職稱**，否則又回到舊系統把組織寫進設定的老路。畫面上「現在誰要簽」由記錄上的 `current_approvers` 欄位與 approver_chain 子表格呈現，永遠是即時真相。

### 5.2 變動深度的處理：同名動作 + 互補 filterCond（kintone 標準技法）

不同申請人的鏈深度不同（課員送單走 5 關、部長送單走 2 關），但原生流程的狀態圖是靜態的。解法不是跳關，而是**每個簽核狀態生成兩條同名「核准」動作，用互補的 filterCond 分流**：

```
簽核中(n) ─ 核准 [filterCond: total_steps > n]  → 簽核中(n+1)
簽核中(n) ─ 核准 [filterCond: total_steps <= n] → 核准（終態）
```

`total_steps`（數值欄）由 adapter 在 submit 時寫入（= chain 長度）。簽核者永遠只看到一顆「核准」按鈕，kintone 依條件自動走對的路——這是 kintone 做 OR 分歧的標準手法，兩條 filterCond 互補、不會同時為空。

### 5.3 標準 adapter 欄位規約（每個申請 App 一致）

| 欄位 | 類型 | 用途 |
|------|------|------|
| `approver_chain` | 子表格 | 現有規劃（建議依評估報告 #3 補 `signing_mode` 欄） |
| `current_approvers` | 使用者選擇（多選） | **原生流程唯一的 assignee 來源**：所有簽核狀態的處理人都設 `FIELD_ENTITY → current_approvers` |
| `current_step` | 數值 | 目前關卡指標 |
| `total_steps` | 數值 | 鏈總長，供 5.2 的 filterCond 用 |

adapter 行為（同一支 JS 掛所有申請 App）：

- **submit（送出申請）**：`buildChainForForm(申請人, 本App ID, {forceFresh: true})` → 寫入 approver_chain / total_steps / current_step=1 / current_approvers=第 1 關解析結果。
- **process.proceed（每次核准）**：讀 approver_chain 第 `current_step + 1` 列的 role_id → **當下即時解析** holder（含代理 overlay，見 docs/07）→ 寫入 current_approvers、current_step+1。「跑到時才解析」語義不變，IT 改群組對在途單即時生效。

**前提條件（必須寫進整合指南）**：process.proceed 內要寫欄位就必須 `return event`，而這會要求**執行者（簽核者）必須具備記錄編輯權限**。具體做法：App 權限開放編輯給簽核者群組，敏感欄位再用欄位權限鎖住、並搭配 JS 設 disabled 防止手動改動。這是 kintone 平台本身的規則，無法繞過，建議及早在權限規劃時就一併考慮進去。

### 5.4 全員會簽的原生限制（誠實分析）

kintone 的 assignee.type（ANY/ALL）是**每個狀態靜態設定**的，不能依記錄動態切換。而個人段每一關落在誰身上因申請人而異——所以「簽核中(n)」無法一下 ANY 一下 ALL。務實的規則：

- **標準模板一律 ANY（任一人簽）**——與角色表 `signing_mode` 預設一致，涵蓋絕大多數關卡。
- **需要全員會簽的關卡，必須是職能段的固定關卡**（位置固定，產生器才能為那一個狀態生成 ALL）。設計需求單收集時就用這條規則把關。
- 個人段裡混用會簽的需求（若真出現）：v2 再議，選項是 adapter 以 JS 攔 proceed 自行計數，複雜度高，不建議先做。

### 5.5 部署管線（產生器取代手動設定 40-50 次）

```
① GET  /k/v1/app/status.json?app={id}         ← 備份現況（含 revision）
② spec 規格檔（每表單一份：路由 App ID + K + 會簽關卡 + 作廢群組）
③ generate                                     ← 由模板展開完整 status.json
④ validate                                     ← from/to 存在性、filterCond 互補、終態 assignee 為空…
⑤ PUT  /k/v1/preview/app/status.json           ← 只寫測試環境，帶 revision 防併發
⑥ kintone 畫面人工確認
⑦ POST /k/v1/preview/app/deploy.json           ← 部署（這步才動正式）
```

樣板政策（宣告一次、全表單自動套用）：每個簽核關卡的駁回路徑、每個非終態的作廢動作、5.2 的互補動作對。**新表單接入 = 建一筆 form_route_config + 埋 4 個規約欄位 + 掛標準 adapter + 跑一次產生器**，從「每表單半天的手動設定」變成「十分鐘」。

## 六、與現有架構的關係圖

```
                 ┌──────────────────┐
   員工 ────────→│ employee_entry    │ 員工 → 起點角色       （HR 維護）
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
   角色 ────────→│ role_definition   │ 角色 → 人/群組 + next （HR 維護）
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
   表單 ────────→│ form_route_config │ 表單 → 段序列         （IT/表單窗口維護）★新增
                 └────────┬─────────┘
                          ↓
              window.ApprovalRouting.buildChainForForm()
                          ↓
        各申請 App（標準 adapter + 4 個規約欄位 + 產生器產出的流程設定）
```

三張表各答一題：**這個人從哪開始（686）、這個角色是誰且下一關是誰（685）、這張單走哪幾段（新表）**。組織異動改 685/686，流程改版改新表，都不碰程式。

## 七、風險與緩解

| 風險 | 緩解 |
|------|------|
| 簽核者需記錄編輯權限（5.3 前提） | 權限規劃期就定案：編輯權開給簽核者群組 + 欄位權限鎖敏感欄；寫入 04-開發者整合指南 |
| 兩個 ANY 簽核者同時按核准（race） | proceed 時檢查 current_step 與動作對應關卡一致，不一致即 event.error 擋下 |
| 產生器 PUT 蓋掉別人手動改的流程 | 一律帶 revision；PUT 前 GET 備份存檔 |
| 職能段角色被停用 | buildChainForForm 展開時即回 error（複用 #2 修復後的空 holder 檢查邏輯） |
| 金額分流等未來需求 | filterCond 天生支援數值條件（如 `amount > 100000` 走不同動作），模型不用改，記入 v2 backlog 即可 |
