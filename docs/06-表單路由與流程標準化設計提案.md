# 06 — 表單路由與流程標準化設計提案

> 版本 **2.0** ｜ 建立日期 2026-07-06 ｜ 最後修訂 2026-09-01 ｜ 作者 Jimmy + Claude
> 回答的問題：「公司有 4-50 個電子表單且只會更多，是否再多一個 App 來設定各表單簽核跑的順序，搭配兩張表實現更完整的自動化簽核？」
> **結論：是，建議新增第三個 App。** 且此設計把 backlog 的「#5 不同申請類型走不同鏈（v2）」與「#14 整合原生流程管理（P8）」一次收斂。

---

## 一、為什麼需要第三張表

現行兩張表回答了「**這個人**送單，鏈長什麼樣」，但回答不了「**這張單**該走哪條鏈」。請假單簽到部長就結束、採購單要多走會計經辦與總務部長、費用報支可能要會計經理——同一個申請人，不同表單，鏈不同。

不加表的替代方案都不及格：

| 替代方案 | 為什麼不行 |
|---------|-----------|
| 每個申請 App 的 adapter 裡寫死自己的加簽關卡 | 40-50 份 adapter 各自為政，回到「改流程要改程式」的老路，違反本專案存在的理由 |
| 角色表加「適用表單」欄位 | 角色與表單是多對多，塞進角色表會讓 80 筆角色爆炸成數百筆組合 |
| 每種表單建一套獨立的角色鏈 | 「MIS－課長」在 50 條鏈裡重複 50 次，換人要改 50 筆，違反 DRY——這正是階段 1 被否定的原因，只是換個維度重犯 |

**正解與本專案一路以來的哲學一致：再加一層 indirection。** 表單 → 路由設定 → 角色，正如員工 → 起點角色 → 人。

## 二、核心洞察：任何申請單的鏈 = 個人段 + 職能段

觀察 Jimmy 列出的標準關卡（主管／次長／部長／會計經辦人／總務經辦人／總務部長），它們天然分成兩類：

```
┌─ 個人段（因人而異）─────────────┐  ┌─ 職能段（因表單而異，固定）──────┐
│ 起點角色 → 課長 → 次長 → 部長    │→│ 會計經辦 → 總務經辦 → 總務部長    │
│ （沿現有 Linked List 往上走，    │  │ （固定的角色序列，直接指定        │
│   走到指定職稱層級即停）         │  │   role_id，與申請人無關）        │
└─────────────────────────────────┘  └─────────────────────────────────┘
```

- **個人段**：完全複用現有兩張表。截止點用角色表**已有的 `title_level` 欄位**表達（「沿申請人的鏈走，遇到第一個 title_level =『部長』的角色即停」），**不需要改角色表結構**。
- **職能段**：固定角色序列，逐關指定 role_id。角色換人依然走角色表/群組，這裡只存「哪個角色」。

一條路由 = 若干段的有序拼接。最常見的形態是「一個個人段 + 零到多個職能關卡」，但模型不限制段數與順序（例如純職能流程可以完全沒有個人段）。

### 3.1 為什麼要有 `skip_title_levels`（v1.1）

`stop_at_title_level` 只能決定**走到哪裡停**，不能表達**路上哪幾層不簽**。但實務需求是「請假單走到部長，中間不簽次長」——這是截斷做不到的。

兩者職責切開後語義很乾淨：

```
stop_at_title_level = 部長      → 決定範圍上界
skip_title_levels   = [次長]    → 決定範圍內誰被跳過
結果：起點 → 課長 → （次長略過）→ 部長
```

實作關鍵：命中 `skip_title_levels` 的角色**照樣沿 `next_role_id` 往下走，只是不 push 進結果**。跳關不是斷鏈。

UI 沿用既有紀律：`segment_type` 切換時條件顯示對應欄位（P7 pattern）、送出時驗證段類型與欄位的配對完整。本表維護者是 IT／表單窗口而非 HR，故 `role_id` 不需隱藏。

**維護分工**：此表由 **IT 或各表單窗口**維護，不是 HR——HR 管「人與角色」，表單窗口管「單據走什麼流程」，職責切開。權限表比照兩表模式另訂。

## 四、引擎 v2 API

```
buildChainForForm(employeeCode, formAppId, options)
  → { ok, chain, error }        // 契約與 buildChain 完全相同
```

行為規格：

1. 查 `form_route_config`（快取，TTL 比照角色表 5 分鐘）：
   - **查無該表單或未啟用 → fallback 走現行 `buildChain()` 全鏈**。既有規劃完全不受影響，已接入的 App 一行都不用改，向下相容。
2. 逐段展開：
   - `員工鏈段`：沿申請人起點角色走 Linked List，走到第一個 `title_level` = `stop_at_title_level` 的角色**（含該角色）**即停；走到 `is_chain_end` 仍沒遇到 → 回 `{ok: false, error}`（設定矛盾，讓維護者立刻知道）。
   - `指定角色段`：直接取該 role_id 的角色記錄。
3. 全部段拼接後，統一走現行 Phase 2（Promise.all 解析 holder）與 Phase 3（組裝子表格）——**這兩階段程式碼原封不動複用**。
4. 循環偵測：visited Set 涵蓋跨段（防止職能段又指回個人段造成重複）。

**待決點（實作前跟 Jimmy 確認）**：

| 待決點 | 選項 | 傾向 |
|--------|------|------|
| 連續兩關解析出同一人（如課長兼會計經辦） | 保留兩關 / 自動合併為一關 | 傾向保留兩關（單純、留簽核軌跡），試點看實際感受再說 |
| 個人段起點就是截止職稱（部長自己送單） | 個人段為空直接進職能段 / 至少含本人一關 | 傾向個人段為空（主管送單不用簽自己） |

## 五、流程管理標準化（40-50 個表單的一致性）

### 5.1 狀態命名模板（全公司統一，v2.0 改版）

**7 個狀態、5 種動作，每個申請 App 逐字元相同——與表單無關、與關卡數無關。**

```
草稿 ──送出──> 簽核中 ⇄ 經辦人確認中 ⇄ 會簽中 ──同意──> 核決
                 │  └──── 自迴圈 ────┘
                 └──駁回──> 駁回 ──再申請──> 草稿
   （每個非終態掛「作廢」SECONDARY 動作，限定群組）
```

| 狀態 | 執行者 | 對應什麼 |
|------|--------|---------|
| `草稿` | 建立者 | 可編輯 |
| `簽核中` | `current_approvers`（ANY） | 員工鏈段的關卡 |
| `經辦人確認中` | `current_approvers`（ANY） | 指定角色段的關卡 |
| `會簽中` | `current_approvers`（**ALL**） | 簽核模式為全員會簽的關卡 |
| `駁回` | 建立者 | 可改後再申請 |
| `核決` | 無 | 終態 |
| `作廢` | 無 | 終態 |

簽核者只看到兩顆按鈕：**同意**與**駁回**。送出／再申請是申請人按的、作廢是管理群組按的。

> **兩條官方文件沒寫、實測 PUT 才打出來的平台規則**（2026-09-01）：
>
> 1. **index 0 的初始狀態，`assignee.type` 只能是 `ONE`。** 填 `ANY` 會被拒：
>    「初始狀態下，執行者的type只能指定為『ONE』。」草稿只有一個候選人（建立者），
>    `ONE` 與 `ANY` 的實際行為相同，改掉沒有副作用。
> 2. **`SECONDARY` 動作的 `executableUser` 是必填**（回「此項必填。」）。
>    所以路由沒設「可作廢群組」時，產生器**直接不產生作廢動作**——作廢不可逆，
>    本來就該限定誰能按，硬給一個「誰都能按」的版本更糟。要作廢就先設群組。
>
> 兩條都已加進 `validateStatusPayload`，PUT 前就會擋下。

- **狀態名絕不綁職稱、也不帶關卡序號**。「簽核中」與「經辦人確認中」的區分是**職能性質**
  （主管 vs 經辦），不是組織位置——使用者看得出卡在哪一類人，而系統不因此依賴任何組織資訊。
- 畫面上「現在誰要簽」由 `current_approvers` 與 `approver_chain` 子表格呈現；
  流程狀態的實際**執行者**由 adapter 呼叫「更新執行者 API」設定（見 §5.3），永遠是即時真相。

### 5.2 變動深度的處理：狀態自迴圈（v2.0 改版）

不同申請人的鏈深度不同（課員送單走 5 關、部長送單走 2 關）。

**kintone 允許一個動作的「執行前」與「執行後」是同一個狀態**（2026-09-01 實機確認）。
所以 N 關的鏈就在 `簽核中` 上自迴圈 N 次，每次由 adapter 換執行者——
狀態圖是靜態的，鏈長是動態的，兩者互不干涉。

走哪一條自迴圈由記錄上的 `next_state` 決定：

```
簽核中 ─ 同意 [next_state in ("簽核中")]       → 簽核中          ← 下一關還是主管
簽核中 ─ 同意 [next_state in ("經辦人確認中")]  → 經辦人確認中     ← 下一關是經辦
簽核中 ─ 同意 [next_state in ("會簽中")]        → 會簽中          ← 下一關要會簽
簽核中 ─ 同意 [next_state in ("核決")]          → 核決            ← 沒有下一關了
```

三個簽核狀態各四條，共 12 條「同意」；`駁回` 同理看 `reject_state`。
簽核者永遠只看到一顆「同意」，kintone 依條件自動走對的路。

`next_state` / `reject_state` 由 adapter 在**進入某一關時**寫好（kintone 解析 filterCond
與「指定欄位」執行者，用的都是按鈕按下**前**的欄位值）。

**這個改版讓 K（最大鏈深）整個消失**：

| v1.x（簽核中(1)…簽核中(K)） | v2.0（自迴圈） |
|---|---|
| 要算 K（掃 686 的 distinct 起點各展開一次） | 不用算 |
| 要 `max_depth`，submit 要擋「鏈比狀態多」 | 沒有上限，不用擋 |
| 組織多一層主管 → 要重新部署每一張表單 | 一行都不用改 |
| 狀態數因表單而異 | 每個 App 逐字元相同 |
| K 變小時不能刪狀態（刪了名字不能再用） | 沒有增減的問題 |
| 全員會簽只能放在「位置固定」的關卡 | 放鏈的哪裡都行 |

### 5.3 標準 adapter 欄位規約（每個申請 App 一致）

| 欄位 | 類型 | 用途 |
|------|------|------|
| `approver_chain` | 子表格 | 現有規劃（依評估報告 #3 補 `signing_mode` 欄，已於 Phase A 完成） |
| `current_approvers` | 使用者選擇（多選） | **目前這一關期望執行者的鏡像**：介面顯示用 + 原生流程「指定欄位」的 fallback；權威來源見下 |
| `current_step` | 數值 | 目前第幾關。**0＝尚未進入簽核**。狀態名不帶關卡序，這一欄是唯一真相 |
| `total_steps` | 數值 | 鏈總長，顯示「第 3 / 5 關」用 |
| `next_state` | 文字（單行） | **按下「同意」後要去哪個狀態**，供 §5.2 的 filterCond 讀 |
| `reject_state` | 文字（單行） | **按下「駁回」後要去哪個狀態**，同上 |

#### 執行者的寫入機制（2026-08-31 定案）

> 背景：在 `process.proceed` 裡改 `event.record.current_approvers` 再 `return event`，
> **當狀態的執行者設為「指定欄位」時常常失效**——kintone 用「按鈕按下前」的欄位值解析執行者
> （已知行為，見 `docs/對話脈絡.md` §9.8）。故不以此為權威機制。

- **權威機制＝「更新執行者 API」** [`PUT /k/v1/record/assignees`](https://cybozu.dev/ja/kintone/docs/rest-api/records/update-assignees/)。
  一等公民端點，用 `kintone.api` 以**登入者身分**呼叫，不需要 API token（仍符合下方誠實限制與 §9.8）。
  只在「狀態已設定執行者」時可呼叫，所以原生設定仍要掛執行者。
- **原生流程管理設定**：每個簽核狀態的執行者設「指定欄位 → `current_approvers`」當 fallback
  （多數情況 proceed 的 best-effort 寫入會生效）；ANY/ALL 靜態設定規則不變（見 §5.4）。

adapter 行為（同一支 JS 掛所有申請 App）：

- **submit（儲存草稿）**：`buildChainForForm(申請人, 本 App ID, {forceFresh: true})`
  → 寫入 `approver_chain` / `total_steps` / **`current_step` = 0** / `current_approvers` = 第 1 關解析結果
  / `next_state` = 第 1 關的 `step_state`。**不必檢查鏈長**（v2.0 起沒有上限）。
- **process.proceed**：依**動作**推進 `current_step`（同意 +1、駁回歸零或退一關、送出進第 1 關）
  → 讀該關 `role_id` → **當下即時解析**執行者（含代理 overlay，見 docs/07）
  → best-effort 寫入 `current_approvers` / `next_state` / `reject_state` / `return event`。
  全員會簽的關卡用「簽名是否已覆蓋所有執行者」判斷是否推進（見 v2.0 修正 ②）。

- **detail.show（安全網，補正 proceed 失效的情況）**：狀態為簽核中(n) 時，比對「目前實際執行者」與
  第 n 關**即時解析**出來的簽核者；不一致 → 呼叫更新執行者 API（帶 `revision`），
  同步把 `current_approvers` 更新為同一組人，然後重整頁面（執行者是頁面載入時由伺服器算的，
  不重整的話正確的人看不到按鈕；補正後下次載入會比對一致，自然收斂）。
  兩個 ANY 執行者併發時，`revision` 衝突就重讀重試一次。

「跑到時才即時解析」的語義完全不變，IT 改群組對在途單即時生效——只是把「怎麼把人寫進去」
從 proceed 改欄位換成呼叫專用端點。

> **v1.4 三處修正**（2026-09-01，實作 Phase D 時發現）：
>
> 1. **`current_step` 在 submit 應寫 0，不是 1。** 原文把「儲存」與「送出」當成同一件事，
>    但標準模板有獨立的「草稿」狀態——儲存只是把單子存成草稿，要再按「送出」才進第 1 關。
>    語義定為：`current_step` = 目前正在簽的關卡，**0 代表還沒進入簽核**（草稿／駁回）。
>    submit 仍先把第 1 關的人寫進 `current_approvers`，因為 kintone 解析「指定欄位」
>    執行者時讀的是**按鈕按下前**的欄位值。
>
> 2. **推進必須由 `nextStatus` 驅動，不能用 `current_step + 1`。**
>    kintone 官方載明：全員會簽的關卡，**每個執行者按一次都會觸發 `proceed`，
>    而狀態不變**，直到最後一人才轉移。用 `current_step + 1` 會讓會簽關卡
>    每有一人簽名就跳一關。判準：`event.status === event.nextStatus` 時只記簽名、不推進。
>
> 3. **安全網比對的對象是「即時解析的結果」，不是子表格的 `expected_signers` 快照。**
>    快照是送單當下的樣子，HR 換人之後它本身就是舊的——拿舊的去比對，
>    只會在「proceed 沒生效」時補正，補不了「角色換人」。改成即時解析後，
>    兩種情況走同一條路徑。

**前提條件（必須寫進整合指南）**：proceed 內 `return event` 與呼叫更新執行者 API 都要求
**執行者（簽核者）具備該筆記錄的編輯權限**。具體做法：記錄權限用「狀態」當條件開放編輯給
簽核者群組，並搭配 JS 設 `disabled` 防止手動改動。這是 kintone 平台規則，無法繞過，
權限規劃時就要一併考慮。

⚠️ **v1.1 補充兩項誠實的限制**：

1. **kintone 的欄位權限無法依流程狀態切換**（記錄權限可以，欄位權限不行）。因此技術上擋不住簽核者蓄意用 REST API 改單據內容——但那已屬舞弊而非誤操作，且有變更履歷可查（稽核由既有外掛負責，見對話脈絡 Q6）。
2. **API token 絕不可寫進前端 JS**。自訂 JS 在使用者瀏覽器執行，token 等於對所有有 App 存取權的人公開。要用 token 從外部更新記錄，必須有 kintone 以外的執行環境（webhook 接收端／serverless）——2026-08-31 確認目前沒有，故全部走前端：以登入者身分呼叫「更新執行者 API」，不涉及 token。

### 5.4 全員會簽（v2.0 改版：限制解除）

kintone 的執行者類型（任一人 ANY／全員 ALL）是**每個狀態靜態設定**的，不能依記錄動態切換。

v1.x 的編號模型因此只能讓「位置固定」的關卡全員會簽——而只要前面有員工鏈段，
位置就隨申請人浮動，等於絕大多數關卡都做不到。

**v2.0 的解法：給會簽關卡一個自己的狀態 `會簽中`（type = ALL）。**
`簽核中` 與 `經辦人確認中` 被所有任一人簽的關卡共用、型別是 ANY；
簽核模式為「全員會簽」的關卡一律停在 `會簽中`。位置不再有任何影響——
**放在鏈的哪裡都行**，員工鏈段也可以指定全員會簽（例如某一關的角色掛的是群組）。

`approver_chain.step_state` 在建鏈時就決定好：
員工鏈段→`簽核中`、指定角色段→`經辦人確認中`、簽核模式為全員會簽者→`會簽中`（優先）。

### 5.5 部署管線（產生器取代手動設定 40-50 次）

```
① GET  /k/v1/app/status.json?app={id}         ← 備份現況（含 revision），可下載成 JSON 檔
② generate                                     ← ★ v2.0：常數模板，唯一的變數是「可作廢群組」
③ validate                                     ← from/to 存在性、同名動作條件不重疊、終態執行者為空…
④ PUT  /k/v1/preview/app/status.json           ← 只寫測試環境，帶 revision 防併發
⑤ kintone 畫面人工確認
⑥ POST /k/v1/preview/app/deploy.json           ← 部署（這步才動正式）
⑦ 回寫 deployed_at / deployed_hash
```

**v1.1 的修正：廢除 repo 裡的 spec 規格檔。** 原設計把「K、會簽關卡、作廢群組」放在 repo 的 spec 檔，但路由本身在 kintone——**兩份設定必然不同步**，而且不同步時沒有任何機制會發現。改為流程管理需要的欄位（`max_depth`、`cancel_groups`、`reject_target`）全部放進路由表主表，一筆記錄就足以產生完整 status.json。

這是 Jimmy 2026-08-31 的要求「路由表跟流程管理要一起搭配著作設計」的具體落實：**路由表是唯一設定源，同時驅動執行期建鏈與部署期產生狀態圖。**

`deployed_hash` 的用途：把 `route_steps` + `max_depth` 雜湊存起來，即可偵測「路由改了但忘記重跑產生器」。40-50 個表單的規模下這是遲早會發生的事故，一個欄位就擋掉。

### 5.6 kintone 改流程設定的三條限制（v1.3 查證；v2.0 後只剩遷移時會踩到）

kintone 對「改流程設定」有三條限制，都不在原設計的考量內，但每一條都會讓重新部署失敗：

| 限制 | 後果 |
|------|------|
| 只能刪除「**沒有任何記錄停在該狀態**」的狀態 | 有一張在途單卡在簽核中(5)，就刪不掉簽核中(5) |
| **刪掉的狀態名不能再用** | 這次 K 變小刪了簽核中(5)，下次 K 變大就再也建不回來 |
| 狀態上有「已指定執行者的記錄」時，**該狀態的執行者指定方式無法變更**（`GAIA_IL35`） | 有在途單時改 ANY↔ALL 會被拒 |

**v1.3 當時的對策是「產生器只增不減」**（狀態數 = `max(算出的 K, 已部署數)`），
因為 K 會隨組織上下浮動，照著刪等於每次縮編都消耗不可回收的狀態名。

**v2.0 之後這三條限制大多不再適用**：狀態是常數，不會因表單或組織而增減，所以沒有
「該不該刪」的問題。唯一會踩到的時機是**從 v1.x 編號模型遷移過來**——舊的
`簽核中(1)…簽核中(K)` 在新模板裡不存在，部署等同要刪掉它們，只要還有一張在途單
停在上面，kintone 就會拒絕整份設定。產生器的 `findLegacyNumberedStates` 會事先掃出來提醒，
比部署失敗後看不懂錯誤訊息好。

**v2.0 起不再需要算 K**：狀態圖與路由完全無關，產生器只是把同一份常數模板貼到目標 App。
`deployed_hash` 的意義也跟著變——從「路由改了沒重跑」變成「**模板改版了，這個 App 還沒重新部署**」。

樣板政策（宣告一次、全表單自動套用）：每個簽核關卡的駁回路徑、每個非終態的作廢動作、5.2 的互補動作對。**新表單接入 = 建一筆 form_route_config + 埋 4 個規約欄位 + 掛標準 adapter + 跑一次產生器**，從「每表單半天的手動設定」變成「十分鐘」。

## 七、風險與緩解

| 風險 | 緩解 |
|------|------|
| 簽核者需記錄編輯權限（5.3 前提） | 權限規劃期就定案：編輯權開給簽核者群組 + 欄位權限鎖敏感欄；寫入 04-開發者整合指南 |
| 兩個 ANY 簽核者同時按核准（race） | proceed 時檢查 current_step 與動作對應關卡一致，不一致即 event.error 擋下；更新執行者 API 帶 revision，衝突重讀重試一次 |
| proceed 改欄位設不到下一關執行者 | 已否決此機制；改用「更新執行者 API」為權威，detail.show 當安全網補正（§5.3） |

| 職能段角色被停用 | buildChainForForm 展開時即回 error（複用 #2 修復後的空 holder 檢查邏輯） |
| 金額分流等未來需求 | filterCond 天生支援數值條件（如 `amount > 100000` 走不同動作），模型不用改，記入 v2 backlog 即可 |

**v2.0 改版內容**（2026-09-01，Jimmy 提出「所有 App 統一 4 種狀態、2 個動作」的需求）：

起因是 Jimmy 指出編號模型**其實還是寫死了**——寫死的是「數量」而不是「名字」：
K 因表單而異、組織長高要重新部署、`簽核中(3)` 對使用者也毫無意義。

關鍵前提由 **Jimmy 實機確認**：kintone 允許動作的「執行前」與「執行後」是同一個狀態。
（我查官方文件三頁都沒明講，社群討論則一致說不行——**社群的說法是錯的**。
幸好問了而不是照推測動手。）

| # | 改動 | 效果 |
|:-:|------|------|
| 1 | `簽核中(1..K)` → 固定 7 狀態（草稿／簽核中／經辦人確認中／會簽中／駁回／核決／作廢）+ 自迴圈 | K 整個消失：不算 K、無上限、組織長高不必重部署、每個 App 的 status.json 逐字元相同 |
| 2 | 新增 `next_state` / `reject_state` 兩個規約欄位 | 狀態不編號後，filterCond 需要有東西可看才知道下一站是主管、經辦、會簽還是已簽完 |

| 5 | 移除 `max_depth` 的計算與檢查、移除 `getDistinctEntryRoleIds` | 對應的程式碼與資料流一併刪除 |

**v2.0 實作時發現的一個新歧義**：自迴圈讓「`會簽中` → `會簽中`」有兩種可能——
會簽還沒簽完，或是這一關簽完了而下一關剛好也是會簽。狀態轉移一模一樣，分辨不了。
解法是不看狀態，改看**簽名是否已覆蓋所有執行者**（`isFinalSignature`）。
