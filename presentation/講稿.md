# 簽核路由引擎 — 逐頁講稿

> 給自己用的口語講稿。每頁分三塊:
> **這頁重點**(一句話)、**講稿**(照著講就行)、**名詞白話**(怕被問到時的備案)。
> 語氣按「我自己做了這個專案、邊做邊學」來寫,不用裝很厲害。

## 第 1 頁 · 封面

**這頁重點**:開場,說這份簡報要講什麼。

**講稿**:

您好,這是我做過最完整的一個專案,叫「簽核路由引擎」,想藉這個專案說明我平常怎麼思考和解決問題。

簡單講,公司的簽核流程本來是寫死在程式裡的,組織只要一變動,工程師就要改程式。我這次用了一個資料結構課本裡的東西——鏈結串列——把簽核順序改成「存在資料表裡」,以後組織怎麼變,都只要改資料、不用改程式。

整個系統是做在 kintone 上面,後面我會講我是怎麼設計的、過程中用到哪些東西。

**名詞白話**:
- **kintone**:日本 Cybozu 出的雲端平台,可以快速建資料表單(叫 App),也支援用 JavaScript 客製功能。
- **簽核鏈**:一張單子送出後,要依序給哪些人核准,例如 課長 → 部長 → 總經理。

## 第 2 頁 · 問題:舊系統把組織圖寫死在程式裡

**這頁重點**:舊系統為什麼難維護——因為它用「組織名稱+職稱」去推算簽核者。

**講稿**:

先講舊系統的問題。

舊系統判斷「下一關給誰簽」的方式,是用程式去看你的職稱和部門名稱。左邊這段就是實際的樣子:`switch` 裡面寫死「課長就找次長、次長就找部長」,部門名稱還要用字串處理去比對,特殊部門再用另外一個陣列寫死。

這樣會發生什麼事?

- 部門改個名字,字串比對就對不上,要改程式。
- 職稱層級調整,要去改 `case`。
- 最慘的是,如果兩關中間要插一個新的審查單位,整個推算邏輯直接崩潰。
- 而且這些都只有工程師能改,HR 想調整流程只能開單給 IT。

所以我的目標很明確:**讓組織異動不要再動到程式碼**。

**名詞白話**:
- **硬編碼(hardcode)**:把會變動的東西直接寫死在程式裡。資料一變,程式就要跟著改,是常見的壞味道。

## 第 3 頁 · 關鍵想法:多加一層,問題就解了

**這頁重點**:設計改了三次才定案,核心是「角色」這個中間層。

**講稿**:

我的設計其實改了三個版本,跟大家分享一下過程。

**第一版**:我想說,每個員工直接填「我的單下一關給誰」,像串珠子一樣串起來就好。但馬上發現問題——如果課長換人,他底下 20 個員工的資料要改 20 筆。等於同一份資訊散在 20 個地方,很明顯不對。

**第二版**:我在中間加了一層「角色」。員工不再指向某個「人」,而是指向「下一關的角色」,例如「業務部課長」這個角色;然後另外一張表記錄「這個角色現在是誰」。這樣課長換人,只要改角色表的那一筆,20 個員工自動跟著變。從改 20 筆變成改 1 筆。

後來查資料才知道這個手法有個說法:「計算機科學的所有問題,都可以靠多加一層間接層解決。」我等於是自己撞到了這個道理。

**第三版**:解決「正在跑的舊單」問題。重要的角色我改成綁 kintone 的「群組」,IT 在後台換群組成員,連跑到一半的單子都會自動換成新的人。

下面三個數字是結果:換人只改 1 筆、插入新關卡只改 1 到 2 筆、程式碼完全不用動。

**名詞白話**:
- **間接層(indirection)**:不直接指向目標,而是指向一個「中間人」,目標變動時只要改中間人。生活例子:你存朋友的「名字」而不是手機號碼,他換號碼你通訊錄不用改。
- **O(N) → O(1)**:演算法的成本表示法。O(N) 是「資料越多要改越多次」,O(1) 是「不管多少人,都只改固定一次」。

## 第 4 頁 · 資料結構:鏈結串列,長在資料表上

**這頁重點**:整份簡報最核心的一頁——我怎麼把課本的鏈結串列搬到 kintone 資料表上。

**講稿**:

這頁是整個專案我覺得最有趣的地方。

學鏈結串列的時候,課本講的是記憶體裡的節點和指標。我做的事情是把同樣的概念搬到資料表上:

- 角色定義表的**每一筆記錄,就是一個節點**。
- 記錄裡有個欄位叫 `next_role_id`,存的是下一關角色的 ID——**這個欄位就是指標**。
- 有一筆勾了「終點」,就等於鏈結串列的結尾(null)。

中間這張圖是鏈結串列最經典的優勢:在「業務課長」和「業務部長」中間要插一個新的審查關卡 P,我只要做兩件事——新增 P 這筆資料、把課長的 next 改成指向 P。其他 78 個角色、500 個員工、所有程式碼,通通不用動。

然後因為 kintone 的 App 本質上就是資料表,我等於是用「關聯式資料」的概念在組這個結構:

- 角色表是節點的集合,`role_id` 是主鍵;
- 員工表存 `entry_role_id`,類似外鍵,代表「這個員工的單子從鏈的哪個節點進入」;
- kintone 群組則是「一個角色對到多個簽核者」的一對多關係。

**名詞白話**:
- **鏈結串列(Linked List)**:一種資料結構,每個節點記著「下一個是誰」,要插入或刪除節點時只要改前後的指向,不用搬動其他資料。
- **主鍵 / 外鍵**:主鍵是每筆資料的唯一編號;外鍵是別張表用這個編號來指向它,兩張表就「關聯」起來了。
- **DAG**:有方向、不會繞圈的圖。我們的鏈允許多個部門匯流到同一個主管,嚴格說起來已經不只是一條線,而是這種圖。被問到再講就好,不用主動展開。

## 第 5 頁 · 系統架構:四層 + 跑到才解析

**這頁重點**:整個系統的分層,以及「簽核者是跑到那一關才查」的設計。

**講稿**:

整個系統可以切成四層,由上往下看:

- **維護層**:IT 管群組成員,HR 管角色表和員工起點表。重點是維護工作交回給對的人,不再是什麼都找工程師。
- **資料層**:就是前面講的兩張表,加上一個嵌在各申請 App 裡的子表格,存這張單的簽核鏈。
- **引擎層**:我寫的核心程式,負責「沿著鏈走一遍、產出簽核鏈」這件事。
- **應用層**:採購、請假這些實際的申請 App,接進來只需要呼叫四行程式碼。

右邊的表是一個我覺得蠻關鍵的設計:**送單的時候,子表格存的是「角色 ID」,不是人名**。流程跑到第三關,系統才去查「這個角色現在是誰」。

好處是:如果單子跑到一半,某個主管換人了,IT 改完群組,這張舊單的下一關就自動是新主管——不用回頭去修任何已送出的單子。

**名詞白話**:
- **延遲解析(lazy resolution)**:不要太早把答案定死,等真正需要的那一刻再去查。就像不要先把「明天的天氣」印在紙上,而是要出門時才看一眼天氣 App。

## 第 6 頁 · 演算法:走鏈、防環、平行化

**這頁重點**:核心函式 `buildChain()` 怎麼運作,分三個階段。

**講稿**:

接下來講核心程式 `buildChain()`,它做的事就是「從起點角色沿著鏈走到終點,產出整條簽核鏈」。我把它拆成三個階段:

**階段一,走結構**。從起點開始,一直跟著 `next_role_id` 走,直到遇到終點。這裡有兩個保護:

- 用一個 `Set` 記錄走過的角色。如果某個角色出現第二次,代表資料被設成繞圈了(A 指 B、B 又指回 A),馬上停下來報錯,不然會無限迴圈。
- 另外設了最多走 20 關的上限,當第二道保險。

**階段二,平行解析**。走完知道有哪幾關之後,要查每一關「實際是誰」。一開始我是一關查完再查下一關,5 關就要等 5 次 API 來回。後來改用 `Promise.all` 讓 5 個查詢同時發出去,等最慢的那個回來就好——估算從大約 1.5 秒縮到 0.3 秒。可以這樣做的前提是,每一關的查詢彼此沒有依賴關係。

**階段三,組裝**。把角色資料和查到的人組成子表格的格式。這段刻意寫成不碰任何 API 的純函式,所以可以直接用單元測試驗證。

**名詞白話**:
- **Set**:一種集合,查「某個東西在不在裡面」非常快,常拿來做「走過了沒」的記號。
- **Promise.all**:JavaScript 裡讓多個非同步動作同時進行、全部完成後再繼續的寫法。
- **純函式(pure function)**:同樣輸入永遠得到同樣輸出、不偷偷碰外部資源的函式。因為行為穩定,最好測試。

## 第 7 頁 · 快取:減少 API 呼叫,還要防撞車

**這頁重點**:角色表全部快取起來,並處理「同時多個請求」的問題。

**講稿**:

走鏈的時候每一步都要查角色資料,如果每次都打 API 會很慢。角色只有 80 筆左右,所以我直接一次全部抓下來,放進一個 `Map` 裡,之後查角色都是直接從記憶體拿。

這裡我踩過、也學到三件事:

**第一,快取要有期限**。資料抓下來放著,HR 改了角色怎麼辦?所以我設了 5 分鐘的有效期(TTL),過期就重抓。另外送單前可以用 `forceFresh` 強制拿最新資料,確保寫進單子的是對的。

**第二,防止同時重複載入**。如果頁面上兩個地方幾乎同時要角色資料,而快取剛好過期,兩邊會同時去打 API,抓兩次一樣的東西。我的解法是:第一個呼叫進來時,把「正在載入的 Promise」存起來;第二個呼叫進來發現有人正在載入,就直接等同一個 Promise。這樣不管同時幾個呼叫,實際只會打一次 API。

**第三,分頁要做滿**。kintone 一次最多回 500 筆。我本來想說角色才 80 筆不會超過,結果真的在別的查詢上踩到截斷問題,後來統一都用 offset 一頁一頁抓到完。

**名詞白話**:
- **快取(cache)**:把查過的資料暫存起來,下次直接用,省掉重查。
- **TTL**:快取的保鮮期,過期就丟掉重抓。
- **race condition(競態)**:多個動作幾乎同時發生、又互相影響,造成偶發性的錯誤。很難重現,所以要在設計上預防。

## 第 8 頁 · 前端部分:沒有框架的環境怎麼寫

**這頁重點**:kintone 客製不能用 React 之類的框架,所以是純 JavaScript 的基本功。

**講稿**:

kintone 的客製開發環境蠻特別的:沒有打包工具、沒有框架,就是把一支支 JS 檔上傳上去跑。所以這個專案的前端,全部是原生 JavaScript。幾個我固定遵守的寫法:

- **每支檔案都用 IIFE 包起來**,也就是定義完立刻執行的函式。因為所有檔案共用同一個全域環境,不包的話變數會互相打架。
- **設定集中管理**:App ID、欄位代碼全部放在一個 config 檔,用 `Object.freeze` 鎖起來防止被改到。
- **safeHandler**:我寫了一個包裝函式,把每個事件處理器都包一層 try/catch,出錯時統一跳視窗提示。這樣不會有某個事件偷偷掛掉、使用者卻不知道。
- 跨檔案要共用的功能,統一掛在 `window.ApprovalRouting` 這一個名稱下面,不要到處污染全域。

UI 的部分,因為使用者是 35 到 55 歲的 HR 同仁,我做了幾個調整:80 幾個角色的下拉改成可以打字搜尋、依單位分組;角色代碼這種技術性的欄位全部隱藏,HR 看到的都是中文;另外做了一個簽核鏈的視覺化預覽,設定完馬上看得到「這條鏈長什麼樣子」,不用憑空想像。

**名詞白話**:
- **IIFE**:寫完立刻執行的函式,`(() => { ... })()` 這種形式,用途是隔離變數範圍。
- **TreeWalker**:瀏覽器提供的 DOM 走訪工具。我用它精準找到「文字節點」去改標題文字,不動到其他結構——之前直接改整塊 HTML,結果把 kintone 原生的欄寬拖曳功能弄壞了,才改用這個。

## 第 9 頁 · 工具:程式不會錯,但資料會

**這頁重點**:這種「資料驅動」的架構,風險從程式轉移到資料,所以要做檢查工具。

**講稿**:

把規則從程式搬到資料表之後,我發現風險也跟著搬家了:程式邏輯很單純不太會錯,但**資料是 HR 手動維護的,一定有設錯的一天**。所以我做了幾個工具:

- **健康檢查**:掃整張角色表,找四種壞資料——繞圈的鏈、走到一半斷掉的鏈、沒有人指到的孤兒角色、沒設定簽核者的角色。
- **模擬器**:隨便選一個員工,模擬跑一次他的簽核鏈,只顯示結果、不真的寫入。上線前或 HR 改完設定,都可以先試跑看看。
- **反向查詢**:平常是查「我的單會給誰簽」,這個工具反過來查「哪些人的單會簽到我」,主管確認自己的管轄範圍用的。
- **批量匯入**:500 個員工不可能一筆一筆建,做了 CSV 匯入,而且先跑一次「預覽模式」,確認沒問題才真的寫入。

另外核心的走鏈邏輯有用 Vitest 寫單元測試,搭配假資料在本機就能測,不用每次都上 kintone 試。文件的部分,規格、欄位對照、進度、還有當初每個設計決策「為什麼這樣選」都有留下來。

**名詞白話**:
- **dry-run**:演習模式,把整個流程跑一遍但不真的動資料,先看結果對不對。
- **Vitest**:JavaScript 的測試框架,寫好測試案例後一個指令全部自動驗證。

## 第 10 頁 · 概念對照表:這個專案讓我用到了什麼

**這頁重點**:把專案裡用到的資訊科學概念整理成一張表。

**講稿**:

這頁是我自己整理的對照表——做完這個專案回頭看,發現課本上學過的東西其實都用上了:

- **鏈結串列**:`next_role_id` 指標,插入關卡只改兩筆。
- **間接層**:角色抽象層,換人從改 20 筆變成改 1 筆。
- **Map 和 Set**:快取查找、走鏈防環。
- **圖**:多部門匯流到同一個主管,健康檢查找環就是圖的環偵測。
- **快取失效**:TTL 加上強制刷新。
- **並發處理**:防止重複載入、`Promise.all` 平行查詢。
- **延遲求值**:跑到該關才解析簽核者。
- **策略模式**:用 `holder_type` 欄位決定走「群組」還是「個人」的解析方式,取代一堆 if-else。
- **純函式**:組裝邏輯不碰 API,方便測試。
- **正規化**:把重複出現的資訊抽成一張表,跟資料庫設計消除重複的想法一樣。

我自己最大的收穫是:這些概念以前是為了考試學的,這次是**被真實需求逼著用出來**的——「課長換人要改 20 筆」這個抱怨,逼出了間接層;「資料可能被設成繞圈」,逼出了 Set 防環。

**名詞白話**:
- **策略模式(Strategy Pattern)**:同一件事有多種做法時,不要用一長串 if-else 分支,而是依某個欄位/條件選擇對應的處理方式,之後要加新做法也不用改舊邏輯。

## 第 11 頁 · 收尾:目前進度與下一步

**這頁重點**:總結這個專案的價值,交代現在做到哪。

**講稿**:

最後總結一下。

這個專案如果只看表面,是「幫 kintone 寫了一堆客製 JS」。但我自己覺得真正有價值的是**資料設計**那一步:把變動最頻繁的東西——也就是組織——從程式碼搬進資料表,程式只負責「沿著鏈走」這個永遠不變的邏輯。方向對了,後面的程式其實都不難。

回頭看做對的三件事:中間層選在「角色」這個剛剛好的位置(不是人、也不是部門);效能上有意識地減少 API 呼叫;還有把 HR 當成真正的使用者去設計介面,維護工作才真的交得出去。

目前的進度:角色定義表的七支程式已經上到正式環境,在真實資料上邊測邊修,正在逐項驗收。接下來是員工起點表的上線測試,然後核心引擎和工具上線,最後選一個申請 App 當試點、試跑兩週,沒問題再全面切換。

以上是這個專案的分享,謝謝您,有任何細節都歡迎追問。

**名詞白話**:
- **試點(pilot)**:不要一次全面上線,先挑一個範圍小的單位試用,確認穩定再推廣,出問題影響也小。
