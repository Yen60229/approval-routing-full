02 · THE INSIGHT

我的設計改了三版才定下來

第二版用的手法,後來查資料才知道有個名字:間接層(indirection)——不直接指向目標,而是指向一個中間層。

階段 1 · 純鏈結串列

我一開始讓每個員工直接填「下一關給誰」。 但馬上發現:課長換人,底下 20 個員工要改 20 筆——同一份資訊散在 20 個地方,這樣不對。

階段 2 · 角色抽象層

我在中間加了一層「角色」:員工指向角色,角色表才記「現在是誰」。 換人只改 1 筆,O(N) → O(1),20 個員工自動跟著變。

階段 3 · 混合架構

為了讓跑到一半的舊單也能換人,我把重要角色改綁 kintone 群組 (GROUP_SELECT),次要角色維持指定個人。 單子裡只存角色 ID,跑到該關才解析成真人。

05 · ALGORITHM

核心函式 buildChain():走鏈、防環、平行化

我把它拆成三個階段,讓「走結構」和「查資料」分開;查詢改成平行之後,5 關鏈估算從 1500ms 降到 300ms。

// Phase 1 走結構:純快取遍歷,O(n) 零 API
const visited = new Set();          // 循環偵測 O(1)
for (let step = 1; step <= MAX_DEPTH; step++) {
  if (visited.has(id)) return '偵測到循環';
  visited.add(id);
  id = role[NEXT_ROLE_ID].value;   // 跟著指標走
}

// Phase 2 平行解析:N 關 holder 同時發出
await Promise.all(roles.map(resolveHolders));

// Phase 3 組裝:純函式,零 I/O
roles.map((r, i) => assembleChainStep(r, holders[i], i+1));
  • 防止繞圈:我用 Set 記錄走過的角色,同一個角色出現第二次就停下報錯
  • MAX_DEPTH = 20:我多設一道上限當保險,就算資料設錯也不會無限迴圈
  • 序列改平行:原本一關查完再查下一關,後來發現各關查詢互不依賴,改用 Promise.all 同時發出
  • 組裝寫成純函式:不碰 API,可以直接用 Vitest 在本機測

06 · CACHING & CONCURRENCY

快取:這兩個問題我是踩到才學會的

一個是快取放久了資料會過期,一個是多個請求同時進來會重複載入——兩個都在開發過程中實際遇到、處理掉了。

// 三道防線(core/02-api-client.js)
const loadAllRoles = () => {
  if (isCacheFresh())  return Promise.resolve();
  // ① TTL 5 分鐘內 → 零 API 呼叫
  if (roleLoadPromise) return roleLoadPromise;
  // ② 進行中的 fetch 直接複用 → 防並發重複載入
  roleLoadPromise = (async () => {
    // ③ 真正 fetch:offset 分頁取全量,寫入 Map
    ... finally { roleLoadPromise = null; }
  })();                // 失敗也能重試
};
  • 分開處理:角色只有 80 筆,我一次全抓進 Map;員工 500 筆改成用到才查
  • TTL 5 分鐘:HR 隨時可能改資料,所以快取設了保鮮期;送單前用 forceFresh 強制拿最新
  • Promise Singleton:把「載入中的 Promise」存起來讓大家共用,同時多個呼叫實際只打 1 次 API
  • offset 分頁:實測踩到 kintone 單次 500 筆上限被截斷,改成一頁一頁抓到完

我學到最多的,是資料設計
